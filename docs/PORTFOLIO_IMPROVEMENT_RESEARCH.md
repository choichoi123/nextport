# 포트폴리오 페이지 개선 연구

기준일: **2026-11-11**. 목적은 사용자 확인에 따라 **이직·채용을 위한 경력 소개 + 프로젝트·기술 경험 기록**입니다. 이번 결과는 제안이며 화면·DB 구조·공개 설정·배포를 변경하지 않았습니다.

## 1. 현재 확인한 모습

| 확인 대상 | 현재 상태 | 제안에 미치는 영향 |
| --- | --- | --- |
| 공개 홈 | 일반적인 인사·태도와 긴 가치관 문단, 애니메이션, 프로젝트 이동 버튼 | 어떤 업무·기술 문제를 맡아온 개발자인지 먼저 전달할 필요가 있음 |
| 공개 프로젝트 목록 | 기존 5개 항목, 개수 제목, 표지·설명·기간·태그 중심 | 대표 사례와 개인 담당 범위를 목록에서도 파악하도록 개선 |
| 공개 표지 | 5개 중 2개 이미지가 로드 완료 상태에서 실제 이미지 크기 0으로 관측됨 | 신규 콘텐츠 노출과 함께 이미지 표시 상태를 확인해야 함. 원인은 이번 연구에서 진단하지 않음 |
| 로컬 자기소개 | `/about-me`에 제목만 존재 | 빈 메뉴를 늘리기보다 홈에 소개·경력·역량을 먼저 완성 |
| 연락·푸터 | 카카오 연락 링크, 템플릿 문구와 연결 주소 없는 SNS 아이콘 | 공개할 실제 연락 채널과 본인 정보를 중심으로 정리 |
| 데이터 연결 | 공개본은 기존 DB, 개인 복제본은 WISEOP 포함 6개. 파주는 초안 단계 | 콘텐츠 준비와 사이트 노출 전환을 구분. 대표작 공개에는 상세·이미지의 방문자 접근 확인 필요 |

공개 홈·목록은 Chrome에서 직접 읽고 화면을 확인했습니다. 모바일·키보드·모든 상세 링크·성능의 전체 검증을 수행한 것은 아닙니다. 로컬의 미배포 수정과 현재 공개본을 같은 버전으로 취급하지 않습니다.

## 2. 두 목적을 한 사이트에서 구성하는 방법

첫 방문자는 짧게 읽어도 역할과 대표 기여를 알 수 있게 하고, 관심 있는 방문자는 상세 기록까지 들어갈 수 있게 합니다.

| 깊이 | 방문자가 알아야 할 것 | 권장 위치 |
| --- | --- | --- |
| 소개 | 어떤 개발자이며 무엇을 맡길 수 있는가 | 홈 첫 화면·핵심 역량 |
| 판단 | 내가 맡은 범위와 해결한 문제는 무엇인가 | 대표 프로젝트 2~3개·프로젝트 카드 |
| 근거 | 어떤 제약에서 무엇을 선택했고 어떻게 확인했는가 | 프로젝트 상세·기술 기록 |
| 다음 행동 | 경력을 더 확인하거나 연락하려면 어떻게 하는가 | 이력서·연락 영역 |

권장 홈 순서: **전문 분야 소개 → 대표 프로젝트 → 근거가 있는 역량·경력 요약 → 최근 기술 기록 → 연락**. 전체 프로젝트와 상세 기록은 별도로 탐색할 수 있게 합니다. 모든 설명을 첫 화면에 넣거나 읽기 전에 여러 효과·버튼을 거치게 만들지 않습니다.

## 3. 추가·보완할 요소와 우선순위

| 순서 | 요소 | 구체 구성 | 예상 범위 |
| --- | --- | --- | --- |
| 1 | 전문 분야 소개 | 어떤 업무를 다루는지 한 문장, 대표 경험 두 문장, 프로젝트·이력서 동선 | 문구·홈 구조 |
| 2 | 대표 프로젝트 | 2~3개만 선별, 실제 화면·문제·담당 범위·대표 해결 사례·상세 링크 | 홈 영역·기존 데이터 재사용 |
| 3 | 역할이 보이는 카드 | 기간·담당·핵심 기여를 읽기 좋은 순서로 표시, 명확한 상세 버튼, 표지·태그 밀도 정리 | 카드·소개 내용 |
| 4 | 역량·경력 요약 | 기술과 실제 적용 프로젝트 연결, 확인된 이력·역할·팀 구성 | 홈 소개 영역 |
| 5 | 이력서·연락 | 승인된 PDF·공개 연락처·GitHub, 연락 방법이 명확한 버튼 | 파일·링크·푸터 |
| 6 | 기술 경험 기록 | 실제 의사결정·문제 해결·회고 글 2~3개부터 시작, 관련 프로젝트와 연결 | 기록 목록·공개용 본문 |

### 첫 소개 문구 후보

> 복잡한 업무 흐름을 지도와 웹 화면으로 연결하는 개발자 최지훈입니다.
>
> 교통약자 이동지원 이용자 앱과 관제 웹을 개발했습니다. React·WebView 프론트엔드부터 Spring Boot 기반 웹 애플리케이션과 외부 시스템 연동까지 경험했습니다.

이는 확인한 프로젝트 범위를 조합한 편집 제안입니다. 지원하려는 직무가 정해지면 프론트엔드 또는 웹 애플리케이션 개발 중 강조점을 조정합니다. 재직 기간·직급·경력 연수·외부 AI 모델 개발 이력은 추정해 넣지 않습니다.

### 대표 프로젝트 후보와 서로 다른 강점

| 후보 | 보여줄 강점 | 준비 상태 |
| --- | --- | --- |
| 부산 WISEOP | 관제 업무 흐름·지도와 데이터 시각화·프론트/백엔드 연동·실패 상태 처리 | 개인 Notion 본문·이미지 보완 완료. 공개 사이트 연결·상세 접근 확인 필요 |
| 파주 바우처 | 이용자 WebView·회원 승인 흐름·지도 기반 위치 선택·백엔드 협업 | 담당 AI 보완 중. 2026.02~05 범위만 사용하고 이후 유지보수는 제외 |
| SET-AI 또는 SE-LAB | 도식 편집·변환 알고리즘 또는 복잡한 편집 화면 | 본인의 기여와 기존 공개 자료를 재검토한 뒤 하나 선정 |

처음부터 세 개를 모두 완성된 대표작으로 노출할 필요는 없습니다. 공개 준비된 항목부터 사용하며, 기존 프로젝트의 기술 사례도 검토해 보완합니다.

### 카드에 담을 정보 예시

```text
[실제 대표 화면]
부산 교통약자 이동지원 WISEOP
수요·차량·재배치 업무를 연결한 관제 웹
담당: 웹 프론트엔드·백엔드·외부 시스템 연동
대표 사례: 결과불명 상황에서 계획을 보존하는 복구 흐름
기간 / 핵심 기술
[상세 사례 읽기]
```

기간 총일수보다 본인 역할과 기여를 우선합니다. 파주처럼 월 단위로 확인된 기간은 `2026.02~2026.05`로 표현할 수 있도록 향후 데이터 표현을 정합니다. 실제 날짜를 월 초·말일로 만들어 넣지는 않습니다.

### 역량은 사용한 근거와 연결

‘React 90%’ 같은 숙련도 수치 대신 **기술 → 실제 담당 기능 → 프로젝트**를 연결합니다. 예: React·모바일 UI → 이용자 가입·접수 화면 → 파주 / 지도·상태 관리 → 수요와 차량 선택·실패 복구 → WISEOP. 프로젝트 수행 기간과 회사 재직 기간은 구분합니다.

### 기술 기록의 시작점

- WISEOP: 요청 접수와 실제 업무 결과를 구분한 UI, 결과불명 상황에서의 사용자 복구 흐름
- WISEOP: 데이터 없음·실제 0·조회 실패를 구분하는 화면·응답 계약
- 파주: 초기 개발 기간의 WebView·지도·회원 승인 흐름에서 실제 선택한 구조와 제약 — 담당 AI의 근거를 받은 뒤 선정

각 글은 **문제 → 제약·실제 검토한 선택지 → 구현 → 확인 결과·한계 → 회고**로 작성합니다. 원 프로젝트 운영 문서·명령·내부 로그를 그대로 공개하지 않습니다. 구현 당시의 판단과 나중에 정리한 해석을 구분합니다. 파주의 제외된 유지보수 사례를 초기 프로젝트 실적으로 다시 끼워 넣지 않습니다.

## 4. 데이터와 구현 방향

- 프로젝트 제목·설명·기간·태그·표지는 Notion 원본을 홈과 목록에서 함께 읽습니다. 프로젝트별 문구와 데이터를 소스에 따로 복사하지 않습니다.
- 대표작 선정용 페이지 ID·표시 순서는 작은 사이트 설정으로 시작할 수 있습니다. Notion 편집자가 직접 선정해야 할 필요가 생기면 선택 필드를 제안합니다. 이번 연구에서 새 필드를 만들지 않습니다.
- 개인 역할은 우선 기존 `Description`을 다듬어 전달할 수 있습니다. 별도 역할·핵심 사례·기간 정밀도 필드가 필요하면 데이터 계약과 카드 영향을 함께 설계합니다.
- 기술 기록은 Notion의 공개용 기록으로 관리하고 관련 프로젝트를 연결하는 방향을 권장합니다. 별도 DB가 필요한지, 기존 상세의 기술 사례 링크만으로 충분한지는 초기 글의 분량·형식을 보고 결정합니다.
- 1차 구현은 현재 Next.js Pages Router·Tailwind와 Notion 상세 링크를 유지합니다. 자체 상세 렌더러는 본문 블록·이미지·링크·캐시까지 관리해야 하므로 별도 후속 범위로 둡니다.
- 이력서·연락처는 사용자가 공개할 실제 파일·주소를 정한 뒤 노출합니다. 지원 문의에 사용한 개인 메일을 공개 연락처로 자동 전용하지 않습니다.

## 5. 적용 순서와 확인 기준

1. **노출 기반 확인:** 공개할 DB·페이지와 연결 권한, 비로그인 상세 접근, 대표 이미지·링크를 확인합니다. 현행 소스와 배포본의 차이도 구분합니다.
2. **핵심 소개 완성:** 홈 문구·대표작·역할 카드·연락을 먼저 구성합니다. 방문자가 외부 상세를 열기 전에도 어떤 일을 맡았는지 이해할 수 있는지 검토합니다.
3. **경력·기록 확장:** 확인된 이력서와 경력 요약, 공개 검토를 마친 기술 기록을 추가합니다. 빈 메뉴나 아직 없는 파일 버튼을 노출하지 않습니다.
4. **품질 확인:** 모바일·데스크톱, 라이트·다크, 키보드 이동·포커스·버튼 이름·표지 대체 설명·제목 구조를 확인합니다. 성능은 측정한 값과 환경을 남기고 추정 수치를 성과로 표시하지 않습니다.

기존 테마 전환·로컬 오류 수정·Notion 조회 개선을 새 UI 구현 완료나 새 배포 검증으로 보고하지 않습니다. 작업용 브라우저 탭은 사용자 요청에 따라 유지합니다.

## 6. 지금 우선하지 않을 것

현재 규모에서는 복잡한 검색·다중 필터, 방명록·회원가입·문의 저장 서버, 운영 중인 시스템을 직접 조작하는 데모, 대형 3D 효과, 빈 블로그 메뉴, 기술 숙련도 점수, 프레임워크 전면 교체보다 위 방문 흐름의 완성을 우선합니다. 이미 있는 `/gallery`는 메모리 게시판 실험이므로 대표 메뉴에 추가할 근거가 약합니다.
