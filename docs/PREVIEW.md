# 메인·전체 프로젝트·미리보기

승인된 예시 디자인을 실제 메인과 전체 프로젝트 화면에 적용했습니다. 실행·검증·공개 배포의 현재 사실은 [현재 상태](CURRENT_STATE.md)에서 관리합니다.

## 화면 경로

| 경로 | 역할 |
| --- | --- |
| `/` | 개발자 소개·대표작 최대 3개·하는 일·연락 |
| `/projects` | 실제 전체 목록·검색·분야 필터·최근 시작 순/이름순 정렬 |
| `/en` | 같은 디자인의 영어 홈·대표 프로젝트 |
| `/en/projects` | 영어 전체 목록·카드·검색·분야·정렬 |
| `/archive` | 이전 홈과 Lottie 보관본. 메인에서 분리하고 검색엔진 수집 제외 |
| `/preview` | 같은 공통 디자인의 확인용 경로. 검색엔진 수집 제외, 무설정에서만 예시 표시 |
| `/preview/og` | B JIHOON OG 두 안·현재 선택·한영 공유 카드 비교. 검색엔진 수집 제외 |

기존 메인을 주석 묶음으로 남기는 대신 `pages/archive.js`에 실행 가능한 보관본으로 옮겼습니다. 주소를 직접 열거나 미리보기의 ‘기존 홈과 비교하기’로 접근할 수 있고, 보관본에서 현재 메인으로 돌아올 수 있습니다.

## 한국어와 English

Pages Router의 `i18n`은 `ko` 기본·`en` 추가와 `localeDetection: false`를 사용합니다. 브라우저 언어만으로 자동 이동하지 않으며 헤더에서 직접 전환합니다. 언어 전환 시 현재 경로·해시와 목록의 검색어·분야·정렬을 유지합니다. 목록 조건은 URL query에도 반영합니다.

공통 문구는 [한영 사전](../lib/portfolio-messages.mjs), 경로 규칙은 [언어 경로 도구](../lib/portfolio-i18n.mjs)에서 관리합니다. 프로젝트 설명은 번역 사전에 복사하지 않고 [Notion 영문 속성](NOTION.md#프로젝트-속성-계약)을 읽습니다. 영어 카드의 상세 버튼은 검증한 `DetailUrlEn`이 있으면 영문 문서로 연결하고 `Case study (English)`로 안내합니다. 없거나 잘못된 주소이면 원래 한국어 상세와 `Case study (Korean)` 안내를 유지합니다. 한국어 화면의 상세 주소는 그대로입니다. 원본 화면 이미지의 한글은 그대로 유지하며 이미지 설명과 구성 스케치의 문구는 해당 언어로 표시합니다.

`/preview`와 `/en/preview`도 언어에 맞는 공통 UI를 사용하며 무설정일 때만 명시적인 예시를 제공합니다. 번역 대상이 아닌 `/archive`·`/about-me`·`/gallery`의 `/en` 주소는 한국어 주소로 이동합니다. 페이지 제목·설명·문서 언어·canonical·hreflang도 표시 언어에 맞춥니다.

## 로컬 실행과 확인

원본 저장소의 실행 방법은 [README](../README.md)를 따릅니다. 평소 로컬 Notion 설정은 비워 두며, 사용자 승인으로 연결한 실데이터 검증 사본은 원본 저장소와 환경파일을 분리합니다. 현재 실행 주소·사본 경로·동기화한 소스는 현재 상태를 기준으로 합니다.

검증용 사본은 원본 저장소의 파일 편집을 자동으로 따라가지 않습니다. 파일을 수정하면 필요한 소스만 사본에 반영하고 화면을 새로고침합니다. 환경파일·인증값·다른 서버의 빌드 산출물을 복사하지 않습니다. 기존 브라우저와 사용자가 유지하도록 요청한 작업 탭은 종료하지 않습니다.

로컬 키를 비운 채 실제 카드 번역을 검토할 때는 공식 Notion 조회에서 허용된 표시 필드만 추린 저장소 밖 스냅샷을 사용할 수 있습니다. 검토용 서버는 제품과 같은 정규화 함수를 사용하고 공개 배포에서 최신 표지를 읽습니다. 스냅샷 확인 시점의 데이터 검증과 실행 중 인증된 API 직접 조회를 구분하며 관리 ID·계정·토큰·본문 전체·서명 이미지 URL을 스냅샷에 넣지 않습니다. 스냅샷이나 공개 조회가 실패하면 예시로 숨기지 않습니다. 실행 위치와 실제 확인 범위는 현재 상태에 기록합니다.

## 데이터 처리

- `/`·`/projects`는 `loadPortfolioProjects`에서 실제 Notion 목록만 받습니다. 무설정은 빈 목록이며 파주 등 예시로 보충하지 않습니다.
- `/preview`의 `loadPortfolioPreview`는 세 연결 설정이 모두 비어 있을 때만 예시 3개를 사용합니다. ‘예시 콘텐츠’와 구성 스케치 구분을 표시합니다.
- 실제 설정의 인증·설정·통신 오류는 그대로 전달하며 예시나 정상 빈 목록으로 숨기지 않습니다. 실제 DB의 빈 응답도 보존합니다.
- 카드 제목·설명·월 단위 기간·태그·표지·상세/GitHub/YouTube 링크는 기존 Notion 계약을 따릅니다. 토큰이나 원본 응답 전체를 클라이언트에 넘기지 않습니다.
- 메인의 대표작은 **부산 WISEOP → 파주 바우처 → 이케이시스 홈페이지** 순으로 확인된 개인 DB 페이지 ID를 우선합니다. 없는 항목은 조회 목록 순서로 채워 최대 3개를 표시합니다. 프로젝트 내용은 원문을 재사용합니다.
- 전체 목록은 확인된 시작 월의 내림차순을 기본으로 하며, 시작 월 미정인 항목은 뒤에 둡니다. 검색·필터·정렬은 클라이언트 표시 순서만 바꾸고 DB를 쓰지 않습니다.
- 실제 역할·핵심 기여를 원문에서 확인할 수 없으면 상세 확인 안내를 표시합니다. 일반 소개를 개인 성과로 바꾸지 않습니다.

표지는 이미지 전체가 보이도록 비율 1.6과 `contain`을 사용합니다. 본문에 올린 화면은 자동으로 커버가 되지 않으며, 커버 URL 누락·실패는 별도 구성 스케치로 대체합니다. API 읽기 허용과 방문자의 Notion 상세 페이지 접근 권한도 구분합니다.

## 공통 화면

- `PortfolioShell`: 사이트 제목·검색 메타·주요 메뉴·테마·푸터. 기존 사이트 확인 메타와 방문 측정은 표준 화면에서 유지하고 미리보기에는 수집 제외 메타를 둡니다.
- `PortfolioHome`: 소개·대표작·역량 설명·기존 공개 연락 링크. 메인에는 미리보기 표시를 붙이지 않습니다.
- `ProjectCard`: 메인·목록의 공통 표지·기간·태그·역할·실제 자료 링크. 예시 모달은 미리보기에서만 동작합니다.
- 전체 목록: 검색어와 분야를 함께 적용하고, 결과 개수·빈 결과·초기화를 제공합니다. 여러 검색어는 모두 포함하는 항목을 찾습니다.

## 로고와 파비콘 전환

[브랜드 설정](../config/portfolio-brand.js)의 `activeBrand` 한 곳에서 `a`·`b`·`c`를 선택합니다. 기본값은 **`b`**이며 B의 연결형 심벌에 C안의 굵은 `JIHOON.` 글자 형태를 참고한 로고입니다. 원래 A·B·C 비교 이미지 6개는 [시안 폴더](assets/brand-concepts-20261112/README.md)에 보존합니다.

```js
activeBrand: 'b', // 'a': 에디토리얼, 'b': 연결형 JIHOON, 'c': 블루/라임
```

브랜드 설정을 바꾼 뒤 개발 서버를 다시 시작하면 로고·파비콘과 기본 `/favicon.ico`가 함께 선택한 안으로 바뀝니다. `npm run dev`와 `npm run build`는 시작 전에 파비콘을 자동 생성합니다. 이미 실행 중인 서버의 기본 ICO까지 갱신하려면 `npm run favicons`를 실행하고 페이지를 새로고침합니다. 운영 사이트에는 수정한 코드를 빌드·배포해야 합니다. 방문자용 선택 메뉴나 Notion 속성은 추가하지 않습니다. 브랜드 설정은 로고와 파비콘만 바꾸며 프로젝트 내용·페이지의 기본 색상은 유지합니다.

- `variants`의 `logo.light`·`logo.dark`는 테마별 로고입니다. `favicon.source`는 보존하는 원본, `favicon.src`는 실제 사용할 작은 PNG, `favicon.sizes`는 그 크기입니다. B의 메인 로고는 라이트·다크 전용 파일을 사용하며 기존 테마 버튼과 시스템 테마를 따릅니다.
- [브랜드 컴포넌트](../components/portfolio/portfolio-brand.js)는 같은 HTML 구조에서 CSS로 로고를 전환합니다. 초기 서버 렌더에서 테마를 추측해 다른 로고 구조를 만들지 않습니다.
- A·C는 원본 비교용 PNG와 파비콘으로 돌아갑니다. 두 안의 메인 로고는 아이보리 배경의 원본을 두 테마에서 공통으로 사용하며 별도 다크 변형을 만든 상태는 아닙니다.
- [생성 스크립트](../scripts/generate-favicons.mjs)는 A·B·C 원본을 수정하지 않고 96·192px PNG와 16·32·48·256px ICO를 만듭니다. `/favicon.ico`에는 활성 브랜드의 ICO를 복사하고 `/archive`도 같은 공통 파비콘을 사용합니다. 이전 화면 본문과 검색 제외는 보존합니다. C안은 생성 이미지로 원본 폰트 파일·폰트명은 없으며, 새 B 로고는 해당 글자 형태와 굵기를 참고해 제작한 이미지입니다.
- 검색엔진용 production HTML의 아이콘은 공개 사이트 기준 절대 URL입니다. `npm run dev`에서는 배포 전 새 파일도 로컬에서 읽도록 같은 파일의 상대 경로를 사용합니다. 생성에는 정상적인 Next.js 16 의존성 설치에 포함된 `sharp`가 필요합니다.

## OG 설정과 시안 비교

[OG 비교 페이지](../pages/preview/og.js)는 최신 B JIHOON 로고를 사용한 두 안을 원본 비율과 한국어·English 320px 기준 공유 카드 예시로 보여줍니다. 현재 선택한 안도 표시합니다. 좁은 화면에서는 비율을 유지해 줄이며 실제 공유 서비스의 표시 방식과 구분합니다. 원본 보기와 PNG 다운로드를 제공하고 Notion 데이터는 조회하지 않습니다. `/en/preview/og`에서도 같은 한국어 정적 비교 페이지를 표시하며 두 주소 모두 `noindex, nofollow`입니다.

- 밝은 안: [PNG](../public/images/og-drafts/og-b-light-20261112.png) · [SVG 편집 원본](../public/images/og-drafts/og-b-light-20261112.svg)
- 딥그린 안: [PNG](../public/images/og-drafts/og-b-deep-green-20261112.png) · [SVG 편집 원본](../public/images/og-drafts/og-b-deep-green-20261112.svg)

PNG는 각각 불투명 RGB **1200 × 630**입니다. SVG는 기존 테마별 B 로고 PNG를 그대로 포함하고 주변 도형·문구를 구성한 원본입니다. 로고 파일은 편집하지 않았으며, 새 문구는 맑은 고딕을 사용합니다. SVG의 문구를 편집할 때는 해당 글꼴이 필요하지만 내보낸 PNG에는 별도 글꼴 설치가 필요하지 않습니다.

기본 OG는 사용자가 선택한 **딥그린 안**입니다. [공유 설정](../config/portfolio-social.mjs)의 한 값만 바꾸면 밝은 안으로 전환합니다.

```js
activeImage: 'deep-green', // 'deep-green' 또는 'light'
```

이 설정은 홈·전체 프로젝트 목록·디자인 미리보기의 한국어와 영어 OG/Twitter 이미지 및 비교 페이지의 현재 선택을 함께 바꿉니다. 방문자의 라이트·다크 테마와는 별개이며 로고·파비콘·Notion은 바꾸지 않습니다. 선택한 PNG의 한국어 문구는 한영 페이지에서 공통으로 사용하고 제목·설명·이미지 alt는 해당 언어를 따릅니다. 페이지 메타 문구는 [한영 사전](../lib/portfolio-messages.mjs)의 `meta`에서 관리합니다.

공유 메타는 설정의 `siteOrigin`을 사용한 절대 이미지 URL, 크기·형식·alt와 `summary_large_image` 카드를 제공합니다. canonical·OG URL·언어별 alternate는 검색어와 해시를 제외한 경로를 사용합니다. 미리보기의 수집 제외와 사이트 확인 메타는 유지합니다. 이전 홈 보관본의 메타·`/opengraph-image.png`도 보존하며 공통 화면에서는 새 설정을 참조합니다.

비교 페이지는 자체 밝은 배경을 사용해 두 이미지를 같은 조건에서 비교합니다. 원본 저장소의 개발 서버는 설정 수정을 반영하지만, 별도 검토 사본은 관련 소스를 동기화해야 합니다. 운영 사이트의 이미지와 메타 변경에는 별도 커밋·배포가 필요하며 공유 서비스의 기존 링크 캐시는 배포 후 다시 확인합니다. 로컬 메타에 운영 절대 주소를 넣는 것과 실제 운영 서버에서 이미지가 제공되는지는 별도로 확인합니다. Notion 상세 URL을 직접 공유할 때의 미리보기는 Notion이 관리합니다.

## 놀이터와 키보드 조작 테스트

- 공통 헤더의 **연락하기 옆 놀이터 / Playground → `/playground` 게임 선택 → 100m 달리기 → 선수 설정·경기·결과·리플레이**로 연결합니다. 놀이터 하위 화면에서도 메뉴 활성 표시와 현재 언어를 유지합니다. 입구의 대표 카드는 100m이며 혼자/가상 경쟁·두 그림체·리플레이와 조작법을 소개합니다. `/playground/controls`는 별도 조작 연습 영역에 보존합니다. 영어는 `/en/playground`와 하위 경로에서 같은 기능을 제공합니다.
- 이후 게임도 `/playground/<게임이름>`의 의미가 드러나는 경로를 사용하고 입구의 카드에서 연결합니다. 화면은 Pages Router의 입구·조작 테스트·달리기·비교 페이지로 구성하며, 외부 게임 엔진은 사용하지 않습니다. 달리기의 온라인 기록 API와 Neon 연결은 아래 절을 따릅니다.
- 테스트에서 **조작 시작**을 누르거나 조작 영역을 클릭/Tab으로 선택합니다. 방향키는 이동, Space는 파동과 동작 횟수, Esc·Tab·영역 밖 클릭은 입력 해제입니다. 키를 놓거나 창·탭을 벗어나면 눌림 상태를 비웁니다. 모바일 폭에서도 화면 버튼을 길게 눌러 반응을 확인할 수 있습니다.
- 입력 처리는 조작 영역에 한정합니다. 버튼·링크와 일반 페이지의 기본 키보드 동작을 보존합니다. 위치는 화면 경계 안에 제한하고, 대각선 속도를 정규화하며 복귀 프레임의 시간 간격을 제한합니다. `prefers-reduced-motion`에서는 파동 애니메이션을 생략합니다.
- 새 페이지는 `noindex, nofollow`이며 기존 sitemap에 넣지 않았습니다. 프로젝트 콘텐츠·Notion 연결·한영 홈·전체 목록·로고·OG·파비콘 설정은 변경하지 않습니다. 로컬 구현과 공개 배포 상태는 현재 상태 문서에서 구분합니다.

### 100m 달리기 작업 재개

100m은 놀이터의 독립 게임입니다. 구현 계약과 수정 진입점은 이 문서에서, 확인 날짜·HEAD·운영 반영·실행 중인 서버·남은 검증은 [현재 상태의 마감·재개 기준](CURRENT_STATE.md#100m-달리기-마감과-재개-기준)에서 관리합니다. 아래 동작 설명은 소스와 대조한 기준이며 과거 DB 계획서의 ‘미구현’이나 오래된 검수 서버 주소보다 우선합니다.

#### 읽기·실행 순서

1. 실제 Git 루트·`git status`·브랜치·HEAD를 확인하고 기존 미커밋과 이번 범위를 나눕니다. `AGENTS.md` → 현재 상태 상단 → 이 절 → 관련 기능·테스트 순서로 읽습니다. 새 게임 개발과 달리기 수정이 동시에 진행 중이면 공통 파일 담당을 먼저 확인합니다.
2. `node --version`, `npm --version`, `npm ls --depth=0`으로 [실행 기준](../AGENTS.md#실행-환경과-커밋-전-버전-확인)을 대조합니다. 일반 재개를 위해 런타임·lock·설치를 바꾸지 않습니다. 실행 중인 서버의 소유자·workdir·사본 여부를 확인하고 비어 있는 포트를 고릅니다. 예전 검수 사본을 현재 루트로 오인하지 않습니다.
3. 루트에서 `npm run dev -- -p <미사용포트>`로 실행합니다. `/playground`는 입구, `/playground/controls`는 조작 연습, `/playground/sprint`는 개발 검수 화면, `/playground/sprint/play`는 운영형 큰 화면, `/playground/sprint/compare`는 네 시안 비교입니다. 한영은 같은 Pages Router 파일과 `locale`을 사용합니다. `/en` 페이지를 중복 작성하지 않습니다. production에서는 기본 sprint도 운영형이며 compare는404입니다.
4. 로컬 기본 Notion·Neon 값을 비워 둔 상태에서는 빈 포트폴리오 목록·로컬 경기·저장 없는 기록 미리보기가 정상입니다. 실제 연동을 확인하려면 승인된 기존 검수 환경과 비공개 연결 위치를 확인합니다. 운영 비밀을 내려받거나 공개 랭킹에 테스트 기록을 등록하지 않습니다. 비교 화면의 시연도 등록 불가입니다.
5. 기능에 맞는 아래 회귀 검증을 수행합니다. production 차이는 환경 파일을 복사하지 않은 별도 사본에서 같은 설치·버전으로 `npm run build` → `npm start -- -p <미사용포트>`로 확인합니다. 실행한 소스·환경·포트를 현재 상태에 기록하며 서버 시작만으로 운영 반영을 표시하지 않습니다.

#### 다른 게임을 개발할 때의 보존 범위

- 새 게임은 별도 Pages 경로·상태·입력/점수 규칙·이미지와 스타일에서 시작하고 입구 카드로 연결합니다. 100m 파일을 범용으로 바꾸거나 같은 게임 상태·응원/리플레이 타이머·입력 리스너를 공유하지 않습니다. 입력은 활성 게임에 한정하고 이탈/숨김 시 정리합니다.
- 새 게임의 저장이 필요하면 별도 API·game/board key·참가자/동점/유효성·보관 정책을 먼저 정합니다. 기존 `sprint-v1`·`sprint-v2`·역대 최고·RPC·익명 쿠키 경로를 재사용하거나 기록을 초기화하지 않습니다. 같은 Neon 리소스를 사용할지 여부는 별도 결정입니다. 포트폴리오 콘텐츠는 계속 Notion 원본을 사용합니다.
- 100m 점수에 영향을 주는 변경은 공통 엔진·서버 입력 검증·리플레이·보드 정책을 함께 검토합니다. 응원0.6m/s를 기존v2에 유지한 승인은 그 조정의 결정이며 다음 규칙 변경까지 자동 허용하지 않습니다. 배포/앱 롤백과 DB 데이터 복구는 별도 작업입니다.

### 100m 달리기와 리플레이

- `/playground/sprint`와 `/en/playground/sprint`는 **선수 설정 → 사이드뷰 100m 경기 → 완주 결과 → 리플레이** 흐름입니다. 이름·닉네임은 NFC 정규화와 앞뒤 공백 정리 후 16 Unicode code point까지, 국적은 ISO alpha-2 국가·지역 목록에서 선택합니다. 국적 기본값은 대한민국이며 주소·계정·IP로 추정하지 않습니다. 시작 전에 혼자 달리기·경쟁과 그림체를 선택합니다.
- 시작 전 실사풍·도트를 선택하고, 경기장 오른쪽 위 버튼으로 경기 중에도 바꿀 수 있습니다. 그림체 전환은 시간·거리·선수 정보·입력 기록을 초기화하지 않습니다. 실제 경기는 사이드뷰를 유지합니다.
- **출발하기 → 이미지 준비 → 서기 1초 → ON YOUR MARK·크라우칭과 3·2·1 → GO → ← 왼발 / → 오른발 교대 입력 → 100m 피니시** 순서입니다. 출발 준비는 총4초이며 경기 기록은 GO 이후부터 잽니다. 첫 유효 입력이 늦으면 준비 자세를 유지하고 입력 뒤220ms 동안 밀고 나가는 자세를 거쳐 달립니다. 새 교대 입력만 추진력을 주며 같은 발 연속 입력·키 자동 반복은 발걸음을 늘리지 않습니다. 입력을 멈추면 자연 감속합니다. 화면 버튼도 한 번 누를 때 한 발씩 동작합니다.
- Space는 응원·함성 연출이며 유효한 달리기 중에는 [아래 조건](#온라인-top10과-neon-연결)의 응원 가속도 적용합니다. Esc·Tab·게임 전체 밖으로 포커스 이동·창 비활성·탭 숨김·메뉴 열기·페이지 이동은 준비/경기를 중단합니다. 경기 조작 영역에서 게임 내부의 그림체·음향 버튼으로 포커스를 옮기면 눌림만 해제하며 경기를 중단하지 않습니다. ‘다시 달리기’는 같은 선수로 재시작하고, ‘선수 변경’은 설정으로 돌아갑니다. 선수 입력 필드의 방향키·Space는 일반 편집 동작을 유지합니다.

### 큰 플레이 화면·테마 HUD·음향·등록 미리보기

- **개발 서버**의 `/playground/sprint`는 기존 선수 설정·진단·자동 시연을 유지하고, `/playground/sprint/play`는 배포 화면을 비교하는 큰 플레이 화면입니다. **프로덕션 빌드**에서는 `/playground/sprint`도 큰 플레이 화면으로 열며 자동 시연·개발 링크를 표시하지 않습니다. 네 가지 비교 경로는 개발 서버에서만 제공하고 프로덕션에서는 404로 처리합니다.
- 큰 화면은 공통 포트폴리오 헤더 아래 전체 높이를 경기장으로 채우며 포트폴리오 푸터를 표시하지 않습니다. 선수 설정·시간/거리·그림체/소리 선택·피니시·리플레이·등록 확인은 게임 화면 안에 배치하고 공통 헤더의 놀이터 메뉴를 사용합니다. 좁은 화면에서는 주자 위치에 맞춰 경기장 카메라를 이동하며 선수 비율과 입력 규칙은 같습니다.
- 큰 화면의 선수 설정·완주 결과·중단 화면에 **놀이터로 돌아가기 / Back to playground** 링크를 제공합니다. 리플레이는 결과로 돌아간 뒤 놀이터로 이동하거나 공통 헤더를 사용할 수 있습니다. 헤더·언어 링크를 포함한 내부 페이지 이동에서 준비 작업·보스 등장·입력·응원 음향을 정리하고 늦은 응답이 뒤늦게 경기를 시작하지 않도록 합니다. 페이지 이탈 시 선수 설정·미등록 경기·리플레이·숨김 호출은 초기화되고 이미 등록한 온라인 기록은 유지된다고 안내합니다. Esc의 경기 중단/리플레이 종료 동작은 그대로입니다.
- 실사풍 HUD·FINISH는 전광판과 금색 숫자·월계 표현, 도트 HUD·FINISH는 **5×7 비트맵 SVG 숫자/문자와 각진 패널**을 사용합니다. 첫 완주·이번 방문 개인 최고 갱신·일반 완주·시연을 구분하고, 갱신 때 이전 기록보다 빨라진 시간을 표시합니다. 온라인 등수나 TOP10 자격으로 해석하지 않습니다.
- 경기 중 Space는 짧은 관중 함성과 응원 연출입니다. 음원은 CC0 실제 관중 녹음의 **3.445초 Ogg**, 최대 게인 **0.16**과 페이드·중복 방지·음소거를 적용합니다. 시작 클릭에서 무음 준비하며 사용자 동작 없이 오디오를 초기화하지 않습니다. 숨긴 탭·포커스가 없는 문서의 재생 요청을 막고, 시스템 음량은 바꾸지 않습니다. 출처와 가공 내용은 [음원 크레딧](../public/audio/playground/sprint/CREDITS.md)에 있습니다.

### 모바일 조작과 실기기 확인

100m 달리기는 화면의 **왼발·오른발 버튼을 번갈아 탭**해서 조작합니다. 캐릭터는 트랙 앞으로 달리며, 두 버튼은 좌우 이동이 아니라 각각 한 발의 입력입니다. 화면의 응원 버튼은 키보드 Space와 같은 동작을 합니다. 별도의 스와이프·가상 조이스틱은 사용하지 않습니다.

작은 화면(1000px 이하) 또는 주 입력 장치가 터치인 환경은 탭 안내를 기본으로 보여 줍니다. 발 버튼에는 `TAP`, 응원에는 동작 이름을 표시하고 선수 설정·조작부·HUD·리플레이에도 한영 터치 안내를 제공합니다. 실제 방향키·Space를 쓰면 키보드 안내로, 화면 발·응원 버튼을 쓰면 화면 버튼 안내로 전환합니다. 명시적으로 선택된 입력 안내는 창 크기 변경이 덮어쓰지 않으며, 이 전환은 경기·누름 상태·공식 기록을 초기화하지 않습니다. 입력 안내와 별개로 두 조작 방식은 항상 사용할 수 있습니다.

작은 화면·터치 장치에서는 왼발·오른발을 같은 넓은 폭으로 배치하고, 세로는 최소 **60px**, 짧은 가로는 **56px** 높이를 확보합니다. 응원은 별도 폭과 간격을 둡니다. 운영형 화면은 상단 기록 정보·가운데 경기장·하단 조작부의 실제 높이를 나누므로, 리플레이에서도 고정 픽셀을 차감하지 않습니다. 짧은 가로에서는 시간·거리·상태/순위를 한 줄로 압축하고 중단·온라인/로컬 표시를 발 버튼 옆에 둡니다. 자세한 터치 안내는 세로에 표시하며 키보드 조작도 유지합니다.

모바일의 **경기 설정** 버튼에서 그림체·소리·TOP10을 열 수 있습니다. 완주·중단 화면에서는 겹치는 도구를 숨기며 완주 요약 아래에 리플레이·기록·다시 달리기·선수 변경을 둡니다. 리플레이의 재생·시점·시간 탐색은 항상 표시하고 **리플레이 설정**에서 속도·처음부터를 조작합니다. 설정은 Escape로 닫고 해당 버튼으로 포커스를 돌립니다. 짧은 화면의 카메라는 선수 발 위치와 보이는 높이를 기준으로 기존 그림을 잘라 표시하며, 선수 크기·거리·속도 계산은 변경하지 않습니다. 짧은 가로에서 모든 경쟁자의 전신을 동시에 보여 준다고 보장하지 않습니다.

선수 설정·기록·TOP10 창은 본문만 스크롤하고 출발·등록/닫기·새로고침 영역을 유지합니다. 모바일 입력은 16px이며, 선수 변경이나 이미 채워진 기록 창을 열 때 입력창 자동 포커스로 키보드를 띄우지 않습니다. 실제 키보드·노치·주소창 변화에 따른 가시 영역은 휴대폰 검수로 확인합니다.

큰 플레이 화면의 작은 화면/터치 장치에서는 **출발 준비부터 ON YOUR MARK·카운트다운 동안** 왼발·오른발을 반투명으로 먼저 보여 줍니다. GO 후 버튼과 같은 위치·크기를 사용하며 응원·상태 행의 자리는 유지합니다. 발 버튼은 실제로 비활성화하고 입력 처리도 경기 중에만 포인터를 저장하므로 준비 중 누른 손가락이 출발 후 자동 걸음으로 이어지지 않습니다. GO 후 손을 떼고 새로 탭해야 합니다. 세로에서는 한영으로 ‘버튼 위치 확인·GO부터 교대’ 안내를 표시합니다. 모바일의 그림체·음향 도구는 준비·GO 표시 동안 잠시 숨겨 카운트를 가리지 않으며, 짧은 가로 화면에서는 카운트 위치·크기를 조정합니다. 데스크톱 마우스 화면과 리플레이에는 준비용 발 버튼을 추가하지 않습니다.

완주 보호는 **1000px 이하 또는 `pointer:coarse`** 환경에 적용합니다. 결과 카드가 **실제로 표시된 시점부터 최소500ms**, **모든 손가락/펜 접촉 해제**, **마지막 접촉 종료 후300ms 동안 새 접촉 없음**을 모두 만족할 때 결과 버튼을 활성화합니다. 연타하면 무접촉 대기가 다시 시작하며, 한 번 해제되면 그 결과에서는 다시 잠그지 않습니다. 경기 입력 해제와 물리 접촉 추적을 분리하고 capture 해제만으로 손을 뗐다고 판단하지 않습니다. 활성화 전 시작된 포인터 클릭은 나중에 도착해도 무시하고 활성화 뒤 새로 누른 클릭만 허용합니다. 잠금 해제 후 키보드·보조기술 클릭에는 선행 포인터 누름을 요구하지 않습니다. 리플레이·기록·재시작·선수 변경과 중복 하단 버튼에 같은 보호를 적용합니다. 1000px 초과이면서 coarse가 아닌 데스크톱 마우스 결과 선택·서버 완주 검증·리플레이 저장은 지연하지 않습니다. 보스 우승 연출이 있으면 총성/결승 시각이 아닌 결과 카드 표시부터 계산합니다.

경기 중 긴 ‘온라인 경기 · 완주 후 서버 검증’과 대응 영문 문단은 표시하지 않습니다. 짧은 온라인 경기 배지·완주 후 검증 상태·등록/제외 이유는 유지하며 ‘왼발·오른발 번갈아 탭 · 길게 눌러도 연타되지 않아요.’와 대응 영문 조작 안내도 유지합니다.

놀이터는 **1000px 이하 또는 터치 장치에서 로고·햄버거 버튼 한 줄 헤더**를 사용합니다. 메뉴를 열면 프로젝트·연락처·놀이터와 언어·테마 전환을 게임 위 패널로 보여줍니다. 메뉴 열기는 진행 중인 경기·준비·함성을 중단하고 조작 연습의 누름 상태를 해제하며, 닫아도 자동으로 경기를 재개하지 않습니다. Escape·메뉴 버튼·배경·Tab 이탈·링크 이동으로 닫을 수 있고, 넓은 데스크톱으로 전환하면 기존 헤더로 돌아갑니다. 일반 포트폴리오 페이지의 헤더와는 별도로 적용합니다.

| 조작 영역에서 게임 내부 도구로 포커스 이동 | 눌림만 비웁니다. 게임 전체 밖으로 포커스를 옮기는 중단 동작과 구분합니다. |

모바일 검수는 viewport만 줄인 PC 브라우저와 **실제 Android Chrome·iPhone Safari**를 구분합니다. 기종·OS·브라우저 버전, 세로/가로 방향과 결과를 함께 남깁니다. 로컬 테스트 서버는 기존 서버와 다른 미사용 포트를 쓰고 기본 빈 DB 설정을 유지합니다. 같은 로컬 네트워크에서 휴대폰이 접근할 수 있는 PC의 실제 네트워크 주소를 사용하며, 접속 실패 시 방화벽·네트워크 격리 설정을 자동으로 해제하지 않습니다. 구체 주소는 비공개 실행 자료에, 실행 상태·검증 결과는 현재 상태 문서에 기록합니다.

실기기에서는 좌우 교대, 두 손가락을 누른 상태에서 한쪽만 해제·재입력, 모두 해제 후 눌림 잔류 여부를 확인합니다. 준비/경기 중 앱 전환·화면 잠금 뒤 중단·무음·자동 재시작 없음, 다음 경기의 정상 입력도 확인합니다. 시스템의 평소 낮은 미디어 음량에서 응원 음량·중첩 방지·음소거·앱 전환 시 정지·복귀 후 자동 재생 없음을 직접 확인합니다. 소프트웨어 gain 값은 특정 기기에서의 체감 음량이나 스피커 측정을 대신하지 않습니다.

현재 함성은 Ogg Vorbis 한 파일입니다. WebKit의 해당 컨테이너 지원은 [Safari 18.4에서 추가](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)됐으므로 구형 iPhone의 디코딩 성공을 가정하지 않습니다. 이 경우 게임 조작과 음향 실패 표시를 구분하며 MP3/AAC 대체 음원은 별도 개선 범위입니다.

### 온라인 TOP10과 Neon 연결

- 게임은 비로그인 방식이며 Neon 관리자 계정과 이용자를 구분합니다. 출발 시 게임 전용 API가 경기 시도를 발급한 뒤 카운트다운을 시작합니다. 완주 시 입력 이력으로 시간을 재계산하고, 등록 시 DB 트랜잭션에서 최신 TOP10과 기존 최고를 다시 확인합니다. 자동 시연·리플레이는 온라인 시도를 발급하지 않습니다.
- 출발 준비4초와 이미지 로딩·보스 등장 시간은 공식 기록에 포함하지 않습니다. `firstStrideAt`은 첫 입력의 출발 자세를 고르는 메모리상 시각이며 제출 필드를 늘리지 않습니다. 현재 경기 규칙은 `sprint-v2`이며 서버와 리플레이의 계산 원점은4000ms로 고정합니다. 기존 `sprint-v1`은3000ms 원점·소수 연산·완주 해시를 보존하여 과거 시도 검증을 지원합니다. 준비 연출 시간과 규칙별 계산 원점은 별도로 관리합니다.
- 공개 항목은 **이름·닉네임, 국적, 0.01초 기록, 서버 등록일시, 순위**입니다. 국적은 이용자 선택이며 서버 등록일시는 DB가 정하는 UTC 값을 현재 지역 시간으로 표시합니다. 이름은 기존과 같이 NFC·공백 정리 후 최대 16 code point이며 같은 이름을 허용합니다.
- 온라인 등록 화면에서는 이름·국적·공개 안내를 확인한 뒤 **등록 / Register**를 한 번 누르면 저장합니다. 중간 확인 요약은 표시하지 않습니다. 입력 오류는 저장 전에 표시하고, 처리 중에는 중복 입력을 막습니다. 응답을 확인하지 못했다면 최초 이름·국적을 고정한 채 같은 요청을 재시도합니다. 오프라인 기록 미리보기는 저장 없이 기존 확인 흐름을 유지합니다.
- 완주 화면의 버튼은 검증 중 **기록 확인 중 / Checking record**로 비활성화하며, 등록 완료 후 **등록 결과 보기 / View registration result**로 바꿔 저장 폼 없이 확정 결과를 다시 엽니다. 뒤늦은 등록 제외도 **기록 판정 보기**를 우선하고, 저장 중은 **등록 중 / Registering**으로 비활성화합니다. 등록 응답 오류를 완료로 표시하지 않으며 기존 고정 내용 재시도를 유지합니다. 처리 중 상세창을 닫으면 비활성 버튼 대신 경기 영역으로 포커스를 복귀합니다.
- 서버 검증 후 기존 개인 최고보다 느리거나 같아 제외된 경기는 **기록 판정 보기 / View record result**에서 이번 기록·기존 최고·차이와 이유를 안내합니다. 이름 입력·등록 버튼과 ‘로컬 미리보기’ 안내를 표시하지 않습니다. 기존 최고는 인증된 완주 판정 또는 등록 재검사의 자기 기록만 사용하며, 공개 순위의 닉네임으로 추정하지 않습니다. 동점·TOP10 기준 미달·미연결·검증 오류는 구분하고, 구형 응답에 이유가 없으면 구체적인 최고 기록을 만들어 표시하지 않습니다.
- 익명 참가자 쿠키는 서버 서명·HttpOnly·SameSite=Lax·게임 API 경로 제한, 운영 HTTPS의 Secure와 **180일** 유효 기간을 사용합니다. 이 브라우저의 최고 1개를 관리하며 이름을 고유키로 쓰지 않습니다. 쿠키 삭제·다른 기기/브라우저까지 같은 사람으로 식별하지 않습니다. 별도의 계정·이메일·IP 기반 신원 추정은 추가하지 않습니다.
- 실사풍·도트·두 카메라는 같은 순위표를 공유합니다. 표시와 저장을 같은 반올림 함수에 맞추고, 동점은 먼저 확정한 등록 순번을 우선합니다. 더 빠른 기록만 갱신하며 순위표당 공개 기록 10개를 유지합니다. 순위 밖의 전체 이력·영구 개인 최고 보관은 별도 기능입니다. 경기 규칙 변경은 기본적으로 `rule_version`과 DB 순위표를 함께 분리하며, 사용자가 같은 보드 내 조정을 명시한 경우에는 기존 기록을 보존하고 변경 전후 조건 차이와 적용 경계를 현재 상태에 기록합니다.
- 현재 `sprint-v2` 보드는 기존 v1 보드·기록·역대 최고와 분리합니다. 기존 설치에는 [v2 보드 추가 SQL](../db/migrations/20261118-sprint-v2.sql)을 DB 소유자의 승인된 관리 경로에서 적용한 뒤 새 앱을 활성화합니다. INSERT만 수행하며 v1 기록을 삭제·변환·이동하지 않습니다. 새 앱은 v1 서버의 시도 응답을 온라인 경기로 수락하지 않고 로컬 플레이로 전환합니다. v2 보드가 없는 서버는 미연결 상태로 처리하며 v1로 조용히 저장하지 않습니다. SQL 파일 작성과 실제 DB 적용 여부는 현재 상태에서 구분합니다.
- 개인 최고와 완주 제외 이유의 상세 응답은 [완주 판정 안내 SQL](../db/migrations/20261118-sprint-finish-eligibility.sql)을 적용한 새 시도부터 제공합니다. 기존 DB에서는 기본 설치·IP 보관·역대 최고·v2 보드 이후에 이 SQL을 적용합니다. 완주 함수의 반환 정보만 추가하며 등록 기준·기존 기록·역대 최고·기존 재시도 캐시는 유지합니다. 앱은 기존 캐시의 새 필드 없는 응답도 처리합니다. **로컬 검증과 운영 DB 적용은 별개**이며 실제 적용 여부는 현재 상태를 확인합니다.
- v2의 응원 입력은 최근500ms 내 유효 발 입력·2걸음 이상일 때350ms 간격으로 최대0.6m/s를 보탭니다. 최고속도12.2m/s는 유지하며, 실제 속도 증가가 수락된 입력만 서버 검증·리플레이 이력에 포함합니다. 길게 누르기 자동 반복·응원만으로 달리기·시연 가속은 허용하지 않습니다. 음소거·음원 실패·음향 재생 제한은 가속 판정과 분리합니다. 게임의 한영 안내와 버튼 명칭은 기존 **응원 / Cheer**를 유지합니다. 2026-11-18 사용자 결정으로0.09에서0.6으로 조정하면서 **기존v2 보드와 저장 기록을 유지**하며 v3를 만들지 않습니다. 변경 전후 경기 조건은 다르고, 반영 전에 시작한 응원 포함 미완료 경기는 새 서버 검증과 맞지 않을 수 있으므로 배포 후 새 경기로 시작합니다. 이미 저장한 기록은 다시 계산하거나 변환하지 않습니다.
- `PLAYGROUND_LEADERBOARD_ENABLED=true`, `PLAYGROUND_DATABASE_URL`, 32바이트 이상의 `PLAYGROUND_SIGNING_SECRET`을 **서버 환경변수**에 설정합니다. 기본 로컬 값은 비워 두고 `.env.example`에는 이름만 둡니다. 기존 Notion 변수와 읽기 연결은 그대로 유지합니다. DB URL·서명 비밀은 `NEXT_PUBLIC_`, 클라이언트 import, 페이지 props, Git·로그에 넣지 않습니다. 실제 개발 연결 위치·검증 사실은 [현재 상태](CURRENT_STATE.md)에 기록합니다.
- 승인된 별도 DB의 소유자 권한으로 [SQL 설치 파일](../db/playground-sprint.sql)을 실행합니다. 이 파일은 `sprint_runtime` 역할과 비공개 스키마·함수를 만들며 반복 실행할 수 있습니다. 전용 역할의 비밀번호는 안전한 관리 경로에서 별도로 설정합니다. 앱에는 소유자 대신 이 역할의 URL을 전달하며, 직접 테이블 읽기·쓰기는 거절하고 필요한 RPC 실행만 허용합니다. 기존 역할이 있다면 역할 속성·멤버십·스키마 소유권을 재확인합니다.
- API는 `POST /api/playground/sprint/attempts`, `POST /finish`, `POST /records`, `GET /leaderboard`입니다. 뒤 세 경로도 같은 `/api/playground/sprint` 접두사를 사용합니다. 서버가 시도·점수·입력 해시와 제출 결과를 고정해 중복 클릭·응답 유실의 재시도를 처리하고, 같은 시도의 다른 내용은 거절합니다. 새 처리를 위한 시도 유효 기간은10분이며 행이 남아 있는 동일 요청은 기존 확정 캐시를 반환할 수 있습니다. 만료24시간 뒤 시도는 정리 대상이 되지만 실제 삭제는 **새 시도 발급 때 최대100개씩 기회적으로** 실행하므로24시간 뒤 물리 삭제를 보장하지 않습니다. 전체 키 입력 원문은 기본적으로 보관하지 않습니다.
- 공유 DB의 빈도 제한·128KiB 요청 제한·최대 4096개 입력·120초 경기 제한을 적용합니다. 유효한 입력을 합성하는 봇이나 쿠키 삭제 후 중복 참여까지 완전히 막는 방식은 아닙니다. 공개 GET은 짧게 캐시하고 매초 polling하지 않으며, 등록 이후 더 오래된 캐시로 순위가 돌아가지 않도록 화면 상태를 보호합니다.
- `미연결`, `정상 빈 순위`, `조회 실패`, `검증 중`, `등록 중`, `등록 완료`, `진입 실패`를 구분합니다. DB가 없어도 기존 로컬 경기·controls·리플레이를 사용할 수 있고 이번 경기의 온라인 등록 불가를 알립니다. 데이터베이스 장애를 빈 정상 목록이나 등록 성공으로 숨기지 않습니다. 개발/운영 DB와 비밀값을 분리하고, 운영 연결·Vercel 환경변수·커밋·배포는 별도 승인 범위로 진행합니다.

#### SQL 설치와 복구 순서

운영 DB가 정상이라면 문서 정리·로컬 재개·새 게임 추가를 위해 SQL을 다시 실행하지 않습니다. 승인된 신규 환경 설치 또는 기존 앞 단계의 재적용이 필요한 경우 DB 소유자 경로에서 다음 순서를 지킵니다. 앱의 연결 역할은 계속 `sprint_runtime`이며 소유자 URL로 바꾸지 않습니다.

1. `db/playground-sprint.sql`
2. `db/migrations/20261118-sprint-registration-ips.sql`
3. `db/migrations/20261118-sprint-world-records.sql`
4. `db/migrations/20261118-sprint-v2.sql`
5. `db/migrations/20261118-sprint-finish-eligibility.sql`
6. `db/migrations/20261120-sprint-maintenance-history.sql`

기본 설치는 기본 등록 함수를 다시 정의하고 함수 실행 권한을 재설정합니다. IP SQL은 이력이 없는 정리 함수로 교체하므로 **기본 파일·앞 단계만 재실행하고 멈추면** 역대 최고·완주 안내·정리 이력 계약이 빠질 수 있습니다. 마지막 단계까지 적용하고 필요한 RPC 권한·반환 필드를 검증합니다. 반복 실행 가능한 SQL이라는 설명은 아무 순서로 실행해도 된다는 뜻이 아닙니다. 기존v1/v2·역대 최고·IP 만료·이력을 삭제하거나 앱 롤백을 이유로 SQL을 역적용하지 않습니다.

`PLAYGROUND_SIGNING_SECRET`은 쿠키 검증과 익명 참가자·빈도 제한 해시에 사용합니다. 임의 교체하면 기존 브라우저가 기존 최고 기록과 연결되지 않거나 진행 중 시도를 이용하지 못할 수 있습니다. 일반 복구·다른 게임 추가를 위해 회전하지 않습니다. 비밀 교체가 필요한 작업은 진행 시도·참가자 연결 영향을 별도로 검토합니다.

#### 관리자용 등록 IP와 보관

- 온라인 TOP10 등록이 성공하거나 기존 개인 최고가 갱신될 때만 서버가 확인한 IP를 비공개 테이블에 저장합니다. 공개 응답·순위표·페이지 props에 IP를 포함하지 않습니다. 등록 전 한국어·영어 안내에는 비공개 수집 목적과 보관·정리 방식을 표시합니다. 국적과 신원은 IP로 추정하지 않습니다.
- Vercel에서는 플랫폼의 `x-vercel-forwarded-for` 단일 IP만 검증해 사용합니다. 로컬에서는 socket 주소를 사용하므로 로컬 검증값은 방문자의 공인 IP가 아닙니다. 값이 없거나 불명확하면 IP를 저장하지 않으며, 요청 본문이나 일반 전달 헤더로 IP를 지정할 수 없습니다. 같은 등록의 재시도는 기존 IP와 만료 시각을 유지합니다.
- IP·역대 최고 설치는 [전체 SQL 순서](#sql-설치와-복구-순서)의 일부입니다. 기본 파일이나 앞 단계만 다시 실행했다면 최신 마지막 단계까지 순서대로 재적용해야 최종 등록 함수·정리 이력이 유지됩니다. 기존 순위는 유지하며 과거 IP를 추정해 채우지 않습니다. 앱 역할은 등록·정리 RPC만 실행하며 IP 테이블·관리자 뷰를 직접 읽을 수 없습니다.
- IP는 등록 시점부터 **30일** 뒤 만료됩니다. 순위 탈락·기록 삭제 때는 더 일찍 삭제합니다. 개인 최고 갱신은 새 등록의 IP·기간으로 교체합니다. 만료 즉시 관리자 뷰에서 제외하고, 물리 삭제는 매일 정리 작업이 실행될 때 이루어집니다. 정기 실행의 지연·실패는 별도 관리 대상이며 정확히 30일 시점의 물리 삭제를 보장하는 방식은 아닙니다.
- `vercel.json`은 매일 **00:00 UTC(09:00 KST)**에 `GET /api/playground/sprint/maintenance`를 호출하도록 설정합니다. 운영에 별도의 무작위 **32바이트 이상 `CRON_SECRET`**을 서버 환경변수로 넣고 배포해야 활성화됩니다. Vercel이 보내는 정확한 Bearer 인증이 필요하며 서명 비밀을 재사용하거나 `NEXT_PUBLIC_`로 공개하지 않습니다. 순위 기능을 비활성화해도 정리는 독립적으로 작동하며 성공 응답에는 상태와 삭제 건수만 있습니다. 운영 Cron의 자동 트리거는 Vercel 실행 기록으로, DB에서 완료한 정리 결과는 아래 비공개 이력으로 구분해 확인합니다. [Vercel의 Cron 보안·실행 안내](https://vercel.com/docs/schedules/cron-jobs/manage-cron-jobs)
- 관리자 확인은 Neon SQL Editor에서 **기존 DB 소유자 권한**으로 아래 뷰를 읽습니다. 별도 공개 관리자 API는 만들지 않습니다. 조회 결과·내보내기·캡처를 공개 자료나 Git에 넣지 않으며, 필요 시 원본 대신 최소한의 비식별 처리 결과만 기록합니다. IP는 NAT·VPN·공유망 때문에 사람을 단정하는 근거가 아닙니다.

```sql
SELECT player_name, country_code, time_cs, recorded_at, registration_ip, expires_at
FROM sprint_private.sprint_registration_ip_admin
ORDER BY recorded_at DESC;
```

#### Cron 비공개 실행 이력

- DB 소유자가 [실행 이력 마이그레이션](../db/migrations/20261120-sprint-maintenance-history.sql)을 IP 보관 마이그레이션 이후에 적용하면 기존 정리 RPC가 `sprint_private.sprint_ip_cleanup_runs`에 **`executed_at`·`succeeded`·`deleted_count` 세 항목만** 저장합니다. 시각은 요청값 대신 DB 실행 시작 시각(시간대 포함)이며 성공 건수0도 정상입니다. 실패 건수는 확정할 수 없어 `NULL`입니다. IP·토큰·요청 헤더·URL·예외 내용·방문자 식별자를 이력에 저장하지 않습니다.
- 기존 설치의 등록·역대 최고·v2·완주 판정 마이그레이션 순서는 유지하고 이 마이그레이션을 마지막에 적용합니다. 앞선 IP 보관 SQL을 다시 실행하면 정리 함수도 이전 본문으로 교체되므로 실행 이력 SQL까지 재적용합니다. 이력 SQL은 재적용해도 기존 순위·역대 최고·시도·IP 만료 정책·저장된 이력을 삭제하지 않습니다. 새 환경변수나 연결 문자열 변경은 필요하지 않습니다.
- 만료 IP 삭제와 성공 이력 저장은 **같은 DB 트랜잭션**입니다. 삭제 오류는 해당 삭제를 롤백하고 실패 이력만 남기며 API는503을 반환합니다. 이력 저장 자체가 실패하면 삭제까지 롤백하여 이력 없는 삭제를 성공으로 표시하지 않습니다. 무인증·잘못된 메서드·설정 오류는 DB 호출 전에 거절되므로 이력을 만들지 않습니다. DB 연결 단절·요청 취소·프로세스 종료처럼 트랜잭션이 완료되지 않은 실패는 같은 DB에 남길 수 없으므로 Vercel 로그와 함께 확인합니다.
- 이력은 DB 소유자만 조회하며 `PUBLIC`·`sprint_runtime`의 직접 조회·쓰기를 허용하지 않습니다. 별도 공개 관리자 API나 화면은 없습니다. 인증된 수동 정리도 같은 이력을 남기므로 세 항목만으로 자동/수동 출처를 식별하지 않습니다. 과거 실행을 소급 생성하지 않으며 실제 운영 적용 여부는 [현재 상태](CURRENT_STATE.md)를 확인합니다.

```sql
SELECT executed_at, succeeded, deleted_count
FROM sprint_private.sprint_ip_cleanup_runs
ORDER BY executed_at DESC
LIMIT 30;
```

로컬 SQL 검증은 운영 접속 없이 메모리 PostgreSQL인 PGlite를 별도 검증 폴더에 준비한 뒤 아래처럼 실행합니다. `PGLITE_MODULE_PATH`는 설치된 패키지의 모듈 진입 파일이며 URL·DB 연결 문자열을 넣는 값이 아닙니다. 루트의 package·lock·설치와 로컬 빈 연동 설정은 유지합니다.

```powershell
$env:PGLITE_MODULE_PATH = 'C:/path/to/isolated/node_modules/@electric-sql/pglite/dist/index.js'
node scripts/verify-sprint-maintenance-history.mjs
Remove-Item Env:PGLITE_MODULE_PATH
```

#### 역대 전체 1위 확정과 등록 연출

기존 Next.js API와 Neon 등록 트랜잭션에서 **서버가 확정한 역대 최고**만 연출합니다. 완주 시의 ‘이번 방문 최고’·경쟁 경기 순위·온라인 TOP10 순위와 별개이며, 공개 순위 캐시나 브라우저의 시간으로 역대 최고를 판정하지 않습니다.

| 서버 판정 | 조건 | 표시 |
| --- | --- | --- |
| `first` | 해당 규칙 순위표의 첫 기준 기록 | FIRST RECORD · 첫 기록 수립 |
| `broken` | 이전 역대 최고보다 엄격하게 빠름 | WORLD RECORD · 새 기록·이전 최고·단축 시간 |
| `tied` | 이전 역대 최고와 0.01초 단위 동점 | 동률 안내, 기존 보유자·시각 유지 |
| `unchanged` | 역대 최고보다 느린 일반 등록 | 기존 등록 완료 안내 |

- 같은 순위표의 잠금을 잡은 등록 트랜잭션 안에서 검증 기록을 비교·저장합니다. 등록되지 않은 경기나 `not_improved`·`not_qualified` 결과는 역대 최고를 바꾸거나 신기록 연출을 만들지 않습니다.
- 역대 최고는 규칙 버전별 비공개 테이블에 현재 최고 1건만 보관합니다. TOP10·경기 시도가 삭제되어도 남으며 IP·참가자 해시는 넣지 않습니다. 도입 시 **현재 남은 TOP10의 최고**로 초기화하고, 재적용 때 더 느린 기록으로 덮어쓰지 않습니다. 도입 전에 삭제된 과거 기록을 복원하는 기능은 아닙니다.
- 성공한 최초 등록 결과의 `worldRecord`에는 판정·이번 기록·직전 역대 최고·단축 시간만 고정합니다. 재시도는 이후 순위가 바뀌어도 같은 판정을 반환하며, 과거 캐시에 이 필드가 없으면 기존 등록 결과만 표시합니다. 서버·클라이언트 모두 필드와 시간 관계를 검증하고 비공개 메타데이터를 공개 응답에서 제외합니다.
- 실사풍은 경기장 조명·금빛 메달과 숫자 강조, 도트풍은 픽셀 제목·계단형 테두리·픽셀 불꽃으로 구분합니다. 새 등록 완료 전환에서만 한 번 움직이고, 같은 결과를 다시 열거나 완주 화면에 남기는 배지는 정적으로 표시합니다. 동률에는 신기록 애니메이션을 적용하지 않으며 움직임 줄이기 설정을 따릅니다.
