### 공개 표현의 경계

사용할 표현은 **회사 최초 운영자 웹 접수 전환, 프론트엔드 전체 담당, WebSocket 수신과 캐시 병합, 연결·화면 구독 분리, 업무 상태와 폼 입력 흐름 정리**입니다.

다음은 구현 성과에서 제외합니다.

- 모든 접수 요청을 WebSocket으로 송신하거나 요청·응답을 완전 매칭한다는 표현.
- SharedWorker 다중 탭 단일 연결 운영 완료, 끊김·누락 없는 동기화 보장.
- 실제 SMS 발송 완료. 현재 활성 전송 화면은 로그와 성공 알림까지입니다.
- 자동배차·최적 경로 엔진 자체 개발, 지속 GPS 스트림. 현재 위치·탑승지 경로 표시는 이와 구분합니다.
- 권한 JSON 기반 전체 화면 생성 완성, 측정되지 않은 속도·업무효율 향상 비율.

본문 정리와 원 프로젝트 결함 수정은 별도 범위입니다. 이번에는 원 프로젝트 소스와 환경을 수정하지 않습니다.

## C. 공개 본문 초안

### 01. 프로젝트 개요

**프로그램에서 하던 접수 업무를 브라우저로, 변경된 접수 내역은 실시간으로.**

WISEVCS 운영자 웹은 상담·접수 담당자가 고객을 찾고, 주소와 이동 조건을 입력해 접수한 뒤 진행 내역을 확인하는 웹 애플리케이션입니다. 회사에서 기존 관제 프로그램의 운영자 접수 업무를 처음 웹으로 전환한 프로젝트입니다.

**기간: 2025.08.25~2026.05.22 / 개발 인원: 백엔드 1명·프론트엔드 본인 1명**

프론트엔드 전체를 담당했습니다. React 화면·라우팅·공통 상태부터 업무 API 연동, WebSocket 수신과 접수 목록 반영, 회원 입력과 지도 UI까지 연결했습니다.

### 02. 해결할 문제

관제 프로그램의 업무를 웹으로 옮기려면 고객 검색·접수·회원 정보와 같은 입력 화면뿐 아니라, 서버에서 달라진 접수 상태를 현재 화면에 반영하는 흐름도 필요했습니다.

개발 중에는 서버 연결이 불안정할 때 소켓 연결 시도가 겹치고, WebSocket 알림이 올 때마다 HTTP로 접수 내역 전체를 다시 조회하는 문제가 있었습니다. 검색·무한 스크롤을 유지하며 새 접수와 변경 내역을 반영하고, HTTP 조회와 실시간 메시지의 서로 다른 형식도 연결해야 했습니다.

검색·선택·입력을 반복할 때 헤더와 본문의 상태가 어긋나거나 회원 모달의 입력과 렌더링이 서로 영향을 주는 문제도 함께 다뤘습니다.

### 03. 내 역할과 시스템 구성

백엔드 개발자와 업무 API·실시간 메시지 규약을 맞추며 웹 프론트엔드 전체를 구현했습니다.

| 영역 | 내 담당 |
| --- | --- |
| 접수·목록 | 고객·기간 검색, 신규 접수, 과거 접수 정보 재사용, 내역·상태 조회와 취소 UI |
| 실시간 수신 | SockJS·STOMP 연결, 이벤트 배포, 메시지 변환, 접수 ID 기준 캐시 병합과 그리드 갱신 |
| 공통 상태 | 로그인 화면 진입 확인, 헤더·사이드바, 검색어·선택 고객·선택 접수 공유 |
| 회원·지도 | 기존 회원 조회·선택, 조회/등록/수정 흐름, 주소·지도 선택과 차량 위치 표시 |

등록·취소와 조회는 **HTTP API**, 서버의 접수 변경 알림은 **WebSocket**으로 처리합니다. 프론트엔드는 두 경로를 하나의 업무 화면으로 연결합니다.

    운영자 브라우저
      ├─ HTTP API → 고객·접수 조회 / 접수 등록·취소
      └─ WebSocket 수신 → 메시지 변환 → 접수 ID별 캐시 병합 → 목록 갱신

React·React Router로 화면 흐름, Redux Toolkit으로 인증 표시 상태를 구성했습니다. SockJS·STOMP와 이벤트 버스는 실시간 수신, AG Grid는 접수 목록, Axios는 업무 API, Kakao Maps는 지도 UI에 사용했습니다.

### 04. 주요 구현과 기술 선택

#### 사례 1. 중복 연결 시도와 재연결을 공통 모듈에서 관리

서버 이상이나 연결 종료 뒤 소켓 연결이 중복되는 현상을 다루며, 화면마다 연결을 생성하는 대신 공통 모듈에서 단일 클라이언트를 관리하도록 구성했습니다.

연결 완료·활성화·연결 진행 상태를 함께 확인해 중복 활성화 시도를 막고 STOMP의 재연결과 양방향 heartbeat를 설정했습니다. 연결이 다시 성립하면 구독을 설정하고 연결·종료·오류 상태를 화면에서 받을 수 있는 이벤트로 전달합니다.

목록 화면은 공통 이벤트를 구독하고 화면을 벗어날 때 구독을 해제합니다. **연결과 화면의 수명주기를 분리**해 연결 관리와 화면 갱신의 책임을 나눴습니다.

#### 사례 2. HTTP 기준 목록과 WebSocket 변경분을 병합

HTTP 조회는 객체형 목록을, 실시간 알림은 배열 형태의 접수 정보를 전달했습니다. 수신 메시지를 화면의 행 구조로 바꾸는 파서를 두고 **접수 ID 기준으로 추가·갱신·삭제**를 적용했습니다.

HTTP로 읽은 기준 데이터와 WebSocket으로 새로 받은 행을 나눠 저장하고, 합칠 때 같은 접수가 중복되지 않도록 했습니다. 화면에서 요구하는 범위가 캐시에 없을 때 HTTP 페이지를 추가 조회합니다.

검색 조건 변경은 캐시 초기화로, WebSocket 수신은 이미 로드한 AG Grid 블록의 갱신으로 연결했습니다. 수신마다 전체 목록을 다시 불러오는 흐름을 줄이면서 **실시간 변경·검색·무한 스크롤을 함께 다루는 구조**를 구현했습니다.

#### 사례 3. 회원 입력과 공통 상태에서 렌더링의 책임을 분리

헤더 검색어와 선택 고객·선택 접수는 공통 레이아웃에서 관리하고 각 페이지가 공유하도록 구성했습니다. 검색 초기화와 다른 페이지 이동이 같은 상태를 기준으로 이어지도록 했습니다.

회원 화면은 조회·등록·수정 모드를 구분하고, 추가설정 모달의 렌더 구조를 바꿔 입력할 때마다 내부 컴포넌트가 새로 만들어지는 패턴을 피했습니다. 행정코드 조회·고객 동기화는 렌더 본문에서 분리해 effect와 이벤트 처리에서 수행하고 같은 지역 요청은 요청키로 중복을 억제했습니다.

누른 검색 필드 우선 처리와 선택한 동명이인 적용, 사이드바가 줄인 **실제 폼 너비를 기준으로 한 container query**, SDK 준비 후 지도를 생성하는 순서도 함께 구성했습니다.

### 05. 결과와 검증

기존 프로그램의 운영자 접수 업무를 웹 프론트엔드로 구성하고, 고객 검색에서 접수·내역 확인으로 이어지는 흐름에 WebSocket 변경 알림을 연결했습니다.

핵심 구현은 **서로 다른 HTTP·실시간 데이터 형식, 연결 상태, 목록 캐시와 화면 선택 상태를 함께 다루는 것**입니다. 실제 구현과 개발 중 확인한 문제를 중심으로 소개하며, 별도 근거가 없는 처리 지연·업무효율·장애복구율 수치는 제시하지 않습니다.

### 06. 관련 자료

표지는 HTTP 업무 요청과 WebSocket 변경 수신을 설명하는 구성 일러스트이며 실제 서비스 화면·동작 증거가 아닙니다.

접수·지도, 접수 목록, 회원정보, 기존 고객 선택 화면을 본문에 배치했습니다. 정지 화면은 각 기능의 구성을 설명하며 실시간 수신·재연결 동작의 검증 자료와는 구분합니다. 실시간 갱신 시연 영상과 공개 저장소 링크는 준비 후 추가합니다.
