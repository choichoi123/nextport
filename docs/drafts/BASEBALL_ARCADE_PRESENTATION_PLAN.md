# 야구 홈런 연출과 음향 계획

기준일: **2026-11-25 KST**. 상태: **1~5 구현·사용자 모바일 정상 확인 완료, 6 입장 팡파르/선수 소개 로컬 구현, 7~9 계획**. 대상은 기존10구 연습·한 타석·선수 육성의 직접 타격 화면이다. 아래 최초 설계와 [추가 연출 계획](#추가-연출-계획--입장수비세리머니구장)을 순차 적용한다. 실제 실행·미확인 범위는 [현재 상태](../CURRENT_STATE.md#야구-입장-팡파르와-선수-소개--2026-11-25)를 따른다.6의 실제 휴대폰 청취는 후속이며 운영 설정·SQL·커밋·배포는 변경하지 않는다.

권장 순서는 **접촉음과 심판 콜 → 확정 홈런 임팩트와 관중 반응 → 짧은 타자 반응과 출루 모션**이다. 실사풍 선수와 경기장을 유지하면서 손맛을 더하되, 접촉 순간의 반응과 안타·아웃·홈런 확정을 구분한다. 전체 베이스 일주와 추적 카메라는 표시 경로를 정리한 다음 검토한다.

| 다음 행동 | 결과가 보이고 사용자가 새로 조작 | 다음 공/타석은 직접 시작한다. 효과가 끝났다는 이유로 자동 진행하지 않는다. |

음향이나 이미지 준비 실패는 기존 타격을 막지 않는다. 늦게 준비된 접촉음은 다음 공에 밀려 재생하지 않고 생략한다. 서버가 늦어지면 결과 확인 상태를 유지하며, 같은 직접 승부를 기다리는 화면에서 확정됐을 때만 결과 반응을 한 번 낸다.

현재 포수 포구 시각/충돌을 따로 계산하지 않으므로 미트 소리는 **존 통과 뒤 짧은 표시용 지연을 둔 추정 음향**으로 다룬다. 존 앞면 통과음과 같은 순간에 틀거나 실제 포구 판정이 새로 생긴 것처럼 취급하지 않는다.

## 홈런 임팩트 권장안

### 접촉 순간의 손맛

기존180ms 파동을 기준으로 일반 접촉은 작은 아이보리 링, 정타는 금색 링과 짧은 잔광으로 구분한다. 파티클은 접촉점 주변의 소수 입자로 제한하고 공·스트라이크존·청록 조준점·자주색 복기 표시는 계속 읽을 수 있게 한다. 강한 접촉도 아웃이 될 수 있으므로 이때 `HOME RUN`이나 홈런 전용 함성은 내지 않는다.

첫 적용에는 실제 시간 정지나 카메라 줌을 넣지 않는 편이 좋다. 현재 화면이 절대시각으로 공과 자세를 그리므로 단순히 프레임을 멈추면 다음 화면에서 공이 건너뛸 수 있다. 필요하면 후속 비교에서 **접촉 후 표시 프레임만30~40ms 유지하는 안**을 별도 시험하되 입력·물리·서버 시각은 계속 진행해야 한다.

### 홈런 확정 순간의 하이라이트

다음 수치는 실제 측정값이 아닌 첫 시안의 권고값이다.

| 상대 시점 | 제안 |
| --- | --- |
| 확정 직후 | 금색 테두리와 `HOME RUN / 홈런` 배너를 나타낸다. 기존 타구 속도·예상 비거리를 함께 보여주고 추정치를 실제 측정값처럼 표현하지 않는다. |
| 처음 약150~250ms | 구장 가장자리의 따뜻한 잔광과 짧은 강조음을 사용한다. 전면 흰 섬광이나 폭발로 공을 덮지 않는다. |
| 약900~1200ms | 배너를 유지한 뒤 결과 카드로 자연스럽게 정리한다. 모바일은 작은 배너로 줄이고 버튼 위치를 밀어내지 않는다. |
| 약1.8~2.4초 이내 | 홈런 관중 반응을 부드럽게 올렸다가 줄인다. 같은 소리의 중첩이나 긴 팡파르 반복을 피한다. |
| 사용자가 다음 공/타석 선택 | 남은 효과·소리를 정리하고 새 경기로 넘어간다. 전 구간을 강제로 보게 하지 않는다. |

장식 레이어는 클릭·터치를 가로채지 않고 경기장/버튼 레이아웃을 바꾸지 않는다. 이전 스윙의 눌림·손 떼기·반복 Space가 다음 타석이나 건너뛰기로 이어지지 않는지 확인한다. 첫 버전에는 배트 플립보다 **타구를 바라보는 마무리와 배트를 내리는 반응**이 현재 실사풍에 어울린다.

홈런은 반드시 공중 담장 통과 판정으로 구분한다. 정타·긴 예상 비거리·바운드 뒤 인정2루타를 홈런으로 바꾸지 않는다. 전체 타구 추적을 만들기 전에는 현재 Scene의 비행선에 임의의 담장을 그려 판정과 맞는 것처럼 보이게 하지 않는다.

### 확정 홈런 가속·섬광 강화안 — 2026-11-25

**상태: 사용자 진행 승인으로 기존`/effects`의 현재형/가속형 비교만 로컬 구현했다. 사용자는 가속형과 ‘모든 페어 타격에 짧게, 홈런 확정 때 강하게 한 번 더’를 선택했다. 실제 한 타석/육성의 기본 연출은 기존형이며 두 단계 시안 확인 후 연결한다.** 사용자는 홈런 때 주변이 가속하는 듯 움직이고 빛이 번쩍이는, 현재보다 강한 아케이드 감각을 원한다. 실사풍 인물·구장은 유지하면서 확정 순간 약0.4초에 강도를 집중하고 기존1.2초 안에 결과 화면으로 정리하는 기준을 시안에 적용했다. 아래 시간·개수·확대값은 설계값이며 실제 휴대폰의 성능/청취 측정값이 아니다. 구현·검증·남은 범위는 [현재 상태](../CURRENT_STATE.md#페어-타격과-홈런의-두-단계-가속-시안--2026-11-25)에 기록한다.

**현재 코드와 시안의 차이:** 실제 한 타석/육성 직접 타격은 접촉 링·타구/첫걸음 표시 뒤 메모리 승부 확정 또는 해당 공의 서버 영수증을 받아 결과 효과를 낸다. 홈런 효과는1200ms의 `HOME RUN` 배너·금빛 halo·입자8개, 관중은최대2.4초다. 별도 카메라 가속·섬광·홈런 세리머니는 없다. `/postplay`는 무음 타구/동작 비교로 홈런 효과 이벤트/배너를 연결하지 않았고, 홈런 표기는 예시 선택/설명이다. `/effects`는 별도 예시 확정 이벤트로 실제 배너/함성을 비교한다. 이 시안의 예시950ms를 실제 수비 처리 시간으로 해석하지 않는다.

| --- | --- | --- |
| 0~160ms | 경기장 외곽 명암이 잠깐 모였다가 샴페인 골드/아이보리 빛이 한 번 번짐 | 공·선수와 중앙 조준/타격 영역 |
| 60~420ms | 장식층의 방사형 속도선이 바깥으로 빠르게 뻗어 가속/줌처럼 보이는 감각을 만듦 | 실제 Canvas 크기·투영·입력 좌표는 유지 |

- **화면 구성:** 딥그린·따뜻한 금빛을 사용한다. 중앙 약55~65%와 결과/미니맵 자리를 비우고 외곽의 선/그라데이션 대비로 강도를 만든다. 기본 후보는PC 속도선10~12개/입자6~8개, 모바일 속도선6개/입자3~4개다. 화면 전체 흰색 반전·반복 섬광·큰 카메라 흔들림은 첫 안에 포함하지 않고 외곽 빛 번짐1회로 비교한다. 섬광의 빈도/면적/대비는 실제 렌더 후 [W3C 섬광 기준](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)을 확인하며, 계획만으로 적합 판정을 내리지 않는다.
- **조작과 시간:** 실제 경기장을 CSS로 확대/이동/흐리게 하거나 게임 시계를 멈추지 않는다. 표시 전용 층에서 가속감을 만든다. 타자가 이미 첫걸음 뒤 사라진 경우 타석에 다시 나타나게 하지 않고, 인물의 홈런 세리머니는 기존8의 별도 결과 컷 후보로 유지한다. 접촉 순간의 공통 손맛과 확정 홈런 연출을 분리해 정타 아웃/긴 타구/인정2루타를 홈런처럼 축하하지 않는다.
- **중복과 취소:** 기존 검증 게이트의 `confirmed:true`인 `result/home-run`에만 연결한다. 같은`id/atMs`를 메인/확대가 공유하고 강한 장식은 현재 사용하는 면 한 곳에 둔다. 설정·한영·표시 면 전환/복구/중복 응답에서 처음부터 번쩍이지 않게 한다. 다음 공/타석·중단·메뉴·이탈은 즉시 정리하며 장식은 클릭/터치를 받지 않는다. 확정 결과·저장·성장·물리/판정 버전을 바꾸지 않는다.
- **강도와 음향:** 기존 ‘기본/약하게/끄기’를 재사용한다. 기본은 가속/한 번의 빛 번짐, 약하게는 배너와 정적인 테두리, 끄기는 장식 생략이다. OS 모션 축소는 속도선/확대/빛 펄스 없이 정적 배너로 구분한다. 기존 타격음·관중 상승/감쇠를 이어 쓰고 새 소리/음량 증가·입장 팡파르 반복을 첫 범위에 넣지 않는다. 음소거에서도 같은 결과가 보인다.
- **모바일 성능:** 큰 `backdrop-filter`나 전체 Canvas 블러/배경 매프레임 재가공을 피하고 경계가 정해진 장식의`transform/opacity`를 먼저 사용한다. [애니메이션 성능 안내](https://web.dev/articles/animations-guide)를 참고하되 실제S22 Chrome/카카오톡·iPhone Safari의 프레임/메모리 결과는 구현 후 확인한다. 별도 전역 애니메이션 루프·입자 누적·새 대형 이미지 필수 로딩은 만들지 않는다.
- **권장 진행:** 먼저 같은3031의 기존`/effects`에서 현재형/가속형을 비교한다. 이 단계는 예시 결과만 사용하고 게임 기록/성장/API/DB를 만들지 않는다. 선택 뒤 실제 한 타석/육성의 공통 확정 홈런 효과에 연결한다. `/postplay`의 조절 시계와 함께 보는 통합 시안은 별도 표시 시계 연동이 필요하며 실제 시계의 효과를 그대로 붙이지 않는다. 새 포트·이미지 생성·DB·커밋/배포를 이번 연구의 실행 사항으로 표시하지 않는다.
- **후속 검수:** 홈런1회, 정타 아웃/인정2루타/파울에서 홈런 효과 없음, 중복/복구/한영 전환 무재생, 연출 도중 다음 행동/중단/앱 전환, 무음/모션 축소, 메인/확대와 모바일 세로/가로의 가독성/넘침을 확인한다.7수비·8세리머니·9구장 생동감을 완료로 바꾸거나 그 구현 승인을 이 연구에서 추정하지 않는다.

### 페어 타격의 첫 가속과 확정 홈런의 두 번째 가속

- 첫 효과는 페어 접촉/정타의 품질에 관계없이 공통으로320ms만 표현한다. 얇은 금빛 외곽과 속도선8개/모바일4개로 타격감을 주고, 홈런 문구·관중 축하·화면 전체 섬광을 먼저 내지 않는다. 파울/헛스윙은 제외한다.
- 두 번째 효과는 기존의 확정`result/home-run`만 사용한다. 홈런 결과의1200ms와 첫 접촉의320ms는 각각 원래 사건 시각에서 계산하고 타격음을 두 번 재생하지 않는다. 안타/정타 아웃/인정2루타에는 두 번째 홈런 가속을 만들지 않는다.
- 첫 효과도 기존 정상/약하게/끄기를 따른다. 정상에서만 추가하고 약하게·끄기·OS 모션 축소에서는 기존 접촉/결과 표현을 유지한다. 중앙 타격 공간·우상단 결과 자리와 클릭/터치를 보호한다. 기존220ms 링 정리로 첫 효과의 시각을 다시 계산하거나 수명을 연장하지 않는다.
- 현재는 같은3031의`/effects`·영문 비교에만 적용한다. 실제 한 타석/육성 연결·메인/확대의 한 곳 소유·실기기 검수는 시안 확인 뒤 진행한다. 새로운 판정·공/배트 물리·저장/성장·DB 계약을 만들지 않는다. 실행 근거는 현재 상태 한 곳에 기록한다.

## 효과음 구성

타격음은 접촉의 질감, 관중과 콜은 결과를 전달하도록 역할을 나눈다. 파울도 강하게 맞을 수 있고 묵직한 타구도 아웃이 되므로 안타/홈런 여부만으로 접촉음을 정하지 않는다.

| 상황 | 소리 제안 | 우선순위와 주의점 |
| --- | --- | --- |
| 릴리스/가까운 공 통과 | 짧고 작은 공기 소리 | 기본. 실제 구속 체감과 함께 조절하되 귀 옆을 과장되게 쏘는 소리는 피한다. |
| 배트 스윙 | 가벼운 휘두름 | 기본. 입력 직후 반응하되 타격음과 구별한다. |
| 약한/보통/강한 접촉 | 나무 배트 샘플2~3종 | 기본. 기존 접촉/품질 값으로 선택하며 게임의 난수 진행을 소비하지 않는다. |
| 파울 | 접촉음 뒤 짧은 파울 콜 | 기본.2스트라이크 파울에도 삼진 콜을 내지 않는다. |
| 지켜본 공·헛스윙 | 포수 미트의 짧은 포구음 | 기본. 실제 접촉한 공에는 예약된 포구음을 취소한다. |
| 스트라이크/삼진 | 짧은 심판 콜 | 기본. 세 번째 스트라이크는 삼진/아웃 콜로 대체해 두 음성을 겹치지 않는다. |
| 볼/볼넷 | 카운트 표시, 선택적인 짧은 음성 | 보조. 매 공 큰 음성보다 자막 중심을 권한다. |
| 안타 | 짧은 관중 상승 | 기본 결과 반응. 안타는 수비 확정 후에만 알린다. |
| 홈런 | 더 풍성한 관중 반응과 짧은 강조음 | 홈런 확정 전용. 큰 배트 소리를 두 번 재생하지 않는다. |
| 아웃 | 짧은 아웃 콜과 낮은 관중 반응 | 패배를 과장하는 부저보다 경기장 분위기를 유지한다. |
| 공 바운드·수비 포구·발소리 | 실제 표시 동작에 맞는 샘플 | 후속. 해당 경로/동작이 보이지 않을 때 임의로 소리를 추가하지 않는다. |
| 경기장 상시 앰비언스·BGM | 낮은 관중 웅성거림, 음악은 별도 선택 | 후순위. 반복 피로와 다운로드를 고려해 첫 단계에서는 제외한다. |

심판 음성은 한국어·영어의 짧은 고정 샘플을 권한다. 방문자 기기마다 달라지는 실시간 TTS를 핵심 타이밍에 사용하지 않는다. 기본은 화면 언어를 따르되 실시간 언어 전환 시 이전 콜을 다시 읽지 않는다. 안타·홈런은 관중/결과 배너로 전달하고 이를 심판의 공식 콜처럼 표현하지 않는다.

처음에는 **전체 음량25% 안팎의 낮은 시작값**, 효과음·심판 콜·관중의 개별 조절을 제안한다. 이는 체감 음량의 측정값이 아니다. 소스별 음량과 피크를 먼저 맞추고 심판 콜 동안 관중을 잠깐 낮춘다.100m의 게인0.16을 다른 샘플에 그대로 복사하지 않는다. 무음에서도 같은 카운트·결과·홈런을 텍스트와 기호로 이해할 수 있어야 한다.

## 웹 음향과 중복 방지

짧은 샘플은 Web Audio의 버퍼 재생을 우선 검토한다. 브라우저는 사용자 동작 없이 소리를 내는 흐름을 제한하므로 소리 켜기/투구 시작의 실제 입력 처리 중 `AudioContext` 생성 또는 `resume()`을 호출한다. DB 응답을 기다린 뒤 처음 해제하려 하지 않는다. 준비 상태와 사용자 음소거 상태도 구분한다. [MDN 음향 권장사항](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices), [Chrome 자동 재생 정책](https://developer.chrome.com/blog/autoplay).

음원은 야구 경로에 진입하고 실제 투구 시작 또는 소리 켜기 입력을 받은 뒤 필요한 묶음부터 받는다. 필수 경기장 이미지와 모든 음원을 한 번에 기다리게 하지 않는다. 디코딩은 비동기이며 완전한 파일을 필요로 하므로 진행 중 로딩이 끝났다는 이유로 지난 사건을 재생하지 않는다. 미지원·로딩 실패는 무음으로 진행하고 재시도 안내를 제공한다. [MDN decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData).

선택한 코덱/컨테이너의 실제 디코딩을 기기별로 검수한다. 기존 Ogg 파일의 사용 이력만으로 새 샘플의 Safari·카카오톡 지원을 확정하지 않는다. 필요하면 MP3/AAC 등 대체 자산을 제공하되 동일 사건의 두 형식을 함께 재생하거나 둘 다 무조건 받지 않으며, 대체 형식도 실패하면 무음으로 계속한다.

- 별도 이벤트 제어부 한 곳이 소리를 재생한다. Canvas의 매 프레임 그리기나 메인/확대 화면 각각에서 재생하지 않는다.
- 접촉 사건은 모드/타석 또는 훈련/공/시도/사건 종류를 조합해 한 번만 처리한다. 확정 결과는 타석/공/최종 결과로 구분한다. 재전송마다 달라질 수 있는 command ID나 revision만으로 중복을 판단하지 않는다.
- 현재 직접 플레이·복구·자동 진행·향후 리플레이·개발 시안을 구분한다. 새로고침/서버 기록 채택/중복 ACK/언어·테마 변경은 과거 소리를 다시 울리지 않는다.
- 육성의 자식 타석이 실시간 연출을 맡고 부모는 성적·성장 갱신을 맡는다. 양쪽이 같은 홈런을 두 번 축하하지 않는다. 자동 진행은 전체 투구음을 빠르게 몰아서 틀지 않고 기본 무음/결산 표시로 처리한다.
- 화면 이탈·메뉴·중단·음소거·새 공·선수 변경 시 예약 소스와 로딩 후 재생 요청을 취소한다. 복귀 후 밀린 소리를 내지 않는다. 음향 해제 실패가 자동 투구나 입력 재수락을 유발하지 않아야 한다.
- 효과음·음성·관중 채널을 나누고 심판 음성/관중은 각각 동시에1개만 재생하는 안을 우선 검수한다. 종료된 노드·이전 타석의 중복 키는 정리해 장시간 플레이에 누적하지 않는다.
- 설정은 야구 전용 브라우저 선호로만 보관한다. 새 음향 설정이나 장식 이벤트를 Neon 원본/성장 보상에 저장하는 계약은 이번 범위에 넣지 않는다. 기존 수집 버전의 화면 출처를 갱신할 필요와 물리/규칙 버전 변경을 구분한다.

음원은 자체 녹음·제작 또는 사용 조건이 명확한 효과음을 선별하고 야구용 출처 문서에 원본/저자/사용 조건/가공을 남긴다. 기존100m 관중 샘플의 재사용은 해당 출처를 다시 확인한 뒤 검토한다. 방송 중계 음성·구단 응원가·특정 심판의 목소리 복제를 기본 재료로 삼지 않는다. 초기 합성 효과/Windows 콜은 타이밍 비교용 이력이며 후속 피드백으로 실제 나무 배트·글러브·공기 마찰·성우 녹음과 관중으로 교체했다. 현재 음원과 가공·저자 표시·사용 조건은 [야구 음원 출처](../../public/audio/playground/baseball/CREDITS.md)를 따른다. 실제 영어 콜을 한영 화면이 공유하고 판정 자막은 한영을 유지한다. 파울/볼넷은 없는 녹음을 합성으로 메우지 않고 화면으로 안내한다.

## 타자 이동과 세리머니

**추가할 가치는 있지만 첫 음향/홈런 작업과 분리하는 편이 좋다.** 현재 타격 뒤 인물이 계속 같은 자리에 있는 아쉬움은 짧은 반응만으로도 줄일 수 있다. 반면 기존 준비 자세를 통째로 미끄러뜨리면 이전에 지적된 인체·접지 문제가 다시 생긴다.

| 단계 | 추천 범위 | 선행 조건 |
| --- | --- | --- |
| 첫 반응 | 타구 바라보기 → 배트 내림, 삼진 후 짧은 아쉬움 | 승인 마무리를 바탕으로 통짜 새 자세를 필요한 만큼만 제작한다. |
| 짧은 출루 | 타석에서1루 방향 첫 몇 걸음 | 좌우 출발 위치·발 접점·그림자·새 동작의 유니폼/번호 영역을 검수한다. |
| 주루 이해 보조 | 결과 미니맵에 주자 점과 도달 베이스 표시 | 기존 `runnerBaseTimesMs`·수비 확정 결과와 연결한다. 새 주력이나 안전 판정을 만들지 않는다. |
| 전체 베이스 일주 | 홈런 후1~3루/홈 도달, 선택적인 짧은 세리머니 | 베이스가 보이는 별도 시점·주자 재생·건너뛰기·경로/음향 동기화를 설계한다. |

새 자세는 현재 실사풍 인물·광원·스폰서 없는10팀 의상을 기준으로 이미지 생성 프롬프트를 만든다. 달리기 게임의 선수를 그대로 붙이거나 몸/관절을 잘라 재조립하지 않는다. 좌우타 출발은 각각 확인하고, 회전 이후 동일 시점의 주루 프레임을 공유할 수 있는지는 별도 비교한다. 원본16장은 덮지 않는다.

짧은 출루의 첫 비교는 좌우별4~6자세 안에서 검토할 수 있다. 다만1024×1536 RGBA 한 장만 약6MiB의 픽셀 메모리가 필요하므로 선택한 손·현재 팀만 지연 준비해야 한다. 이는 픽셀 수로 계산한 추정이며 실제 기기 측정은 아니다.10팀/양손을 미리 합성하거나 새 동작을 첫 입장 필수 로딩으로 만들지 않는다. 실패하면 기존 승인된 마무리를 유지한다.

## 함께 챙길 표현과 보류할 기능

- **타구 경로와 수비 결과의 표시 정합성:** 현재 Scene의 `sampleBaseballBattedBall`과 수비의 `fieldResult.path / decisionPoint / playTimeMs`는 별도 표시 구조다. 홈런 추적·수비/주루를 확대할 때는 이미 확정된 경로를 재생해야 한다. 이를 이유로 물리나 수비 결과를 다시 계산해 바꾸지 않는다.
- **결과의 위계:** 접촉·정타와 최종 안타·아웃·홈런을 화면 용어에서도 구분한다. 강한 타구의 아웃, 볼넷, 삼진에도 짧은 반응을 두어 홈런만 살아 있는 화면이 되지 않게 한다.
- **연출 설정:** 기본/약하게/끄기와 전체 음소거를 작은 설정 메뉴 안에 둔다. 새 버튼 때문에 모바일 타격장이 줄지 않도록 한다. 장식 파티클·배너는 기존 카운트·조준·버튼을 가리지 않는다.
- **모션 축소:** OS의 `prefers-reduced-motion`에서는 장식 흔들림/줌/파티클을 줄이고 정적인 결과를 유지한다. 실제 투구 궤적이나 입력 시간을 바꾸는 기능과 구분한다. [W3C 상호작용 애니메이션 안내](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html).
- **섬광과 음성 안내:** 반복 흰색/빨간 전면 섬광은 설계에서 제외한다. 홈런 정보는 색만으로 전달하지 않고 한 곳의 결과 안내가 읽도록 한다. 기준은[W3C 섬광 안내](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)를 참고하며, 이 계획만으로 접근성 적합성 검증을 마쳤다고 표시하지 않는다.
- **후순위:** 상시 BGM·관중 애니메이션·배트 플립·진동·풀3D 전환·온라인 관전·전체 리플레이는 첫 적용에서 제외한다. 기존 성장 밸런스/실기기 검수와 이번 감각 표현을 구분하며 효과만으로 성장/보상을 늘리지 않는다.

첫 구현은 **1~3순서까지 묶고4의 실기기 검수로 마무리**하는 안을 권한다. 홈런이 나올 때까지 반복 타격해야만 효과를 고를 수 없도록 같은3031의 개발용 효과 시안을 검토한다. 시안의 합성 결과는 실제 경기·성장·DB/API로 전송하지 않으며, 실제 승부 판정과 분리한다. 별도 포트나 화면마다 새 서버는 만들지 않는다.

후속5는 한 타석/육성 직접 타격의 기존 수비 경로·판정 지점을 표시하고, 원래 스윙 뒤 배트 내림→1루 방향 최대4m의 첫걸음만 연결한다. 삼진·볼넷은 현재 승부의 확정 뒤 중립 배트 내림을 보여준다. 고개 숙임·배트 플립·전체 베이스 일주·새 리플레이는 구현한 것으로 설명하지 않는다. 새 전신 이미지는 별도 선택 자산이며 늦은 준비·실패가 기존 타격을 막지 않는다. `/playground/baseball/postplay`는 기존 모델로 계산한5개 예시의 개발용 시각 비교이며 실제 기록을 만들지 않는다.

음향/임팩트는 표시 전용 모듈과 훅을 최소 범위로 추가하고 기존 Scene/10구/한 타석의 사건 전달을 연결한다. 구현 후 필요하면 전용 테스트를 두되 별도 오디오 프레임워크나 범용 사건 버스부터 도입하지 않는다. SSR에서 오디오 객체를 만들지 않고, 개발 시안이 배포 청크에 남지 않는지도 확인한다.

## 검수 항목

1. **판정 보존:** 같은 입력/seed의 접촉·파울·정타·수비 결과·점수·성적·성장 사건이 효과 ON/OFF와 무관하게 같다.4구종/좌우투·좌우타·메인/확대·키보드/클릭/터치를 검사한다.
2. **결과 구분:**2S 파울·루킹/헛스윙 삼진·볼넷·정타 아웃·안타·홈런·인정2루타를 구분한다. 홈런/삼진 관련 음성을 겹치지 않는다.
3. **저장 흐름:** 현재 직접 플레이의 새 결과·서버 지연/실패·동일 명령 재전송·새로고침·서버 기록 채택·다른 탭 충돌·자동 진행을 구분한다. 과거 결과는 무음이며 실제 저장/보상을 반복하지 않는다.
4. **실시간 입력:** 공 통과/접촉 소리를 클릭 시점으로 잘못 옮기지 않는다. 공/존/조준점 좌표·110ms와 투구 clock을 그대로 유지하고, 효과가 다음 공 입력을 대신하지 않게 한다.
5. **음향 수명:** 처음 진입·음소거·작은 음량·초기 로딩/실패·빠른 다음 공·앱 전환·화면 잠금·복귀·페이지 이탈·개발 HMR에서 갑작스러운 소리/밀린 콜/끊임없는 반복이 없다.
6. **기기/성능:** 데스크톱과320px 작은 세로·낮은 가로를 확인하고 실제 S22 Chrome/카카오톡·iPhone Safari에서 첫 접촉 지연·함성 크기·콜 가독성·음원 디코딩/대체 형식·끊김·로딩/메모리를 비교한다. Bluetooth 지연·스피커 음량은 코드/가상 화면 검사와 별도 청취 항목이다.
7. **출처/공개:** 음원/이미지의 출처·가공과 필요한 파일만 남기고 토큰/관리ID/내부 자료를 넣지 않는다. 기존10구/D/E 기록·Notion·Neon·100m을 보존하며 커밋/운영 공개·배포는 별도 요청 범위로 둔다.

### 6. ‘빠라밤 빠 빠밤’ 입장 효과음

- **선택 상태:** 초기에는 짧은6어택의 오리지널 브라스를 제안했고, 이후 사용자가 제공한 「Charge」 첫6음의2초 브라스 재연주를 선택해 실제 입장곡에 적용했다. 미선정 후보로 되돌리거나 현재 실기기 청취까지 완료한 것으로 쓰지 않는다.
- **실사풍 질감:** 실제 브라스/오르간 녹음 또는 자연스러운 악기 소스·짧은 구장 잔향·먼 PA 스피커 느낌이 초기 비교 기준이었다. 현재 선택한 브라스와 원음 보관·제작 근거는 `CREDITS.md`와 현재 상태를 따르며 얇은 전자음·Windows 음성/TTS로 되돌리지 않는다. 실기기 음량·질감은 후속 검수다.
- **길이와 빈도:** 최초 연구는 약1.2~1.5초였으며, 이후 사용자가 확인한 「Charge」 첫6음의 브라스 재연주2초를 공통 팡파르1개로 선택했다. 음원 재생/소개/시안 완료 길이도 함께 맞춘다.10구는 새 훈련 입장 때1번, 한 타석/육성 직접 타격은 사용자가 새 타석을 시작할 때1번이다. 다음 공·같은 공 재준비·복구/조회/동일 명령 재전송·자동 진행·테마/언어 변경에는 울리지 않는다. 팀별10곡은 반복 피로/용량을 비교한 뒤 선택한다.
- **시점:** 입장 클릭/탭 처리 중 음향을 준비하고, 새 입장 표시가 준비됐으며 아직 그 입장을 기다리는 경우에만 재생한다. 서버 응답 뒤 처음 `AudioContext`를 해제하려 하지 않는다. 빠르게 투구를 시작하면 입장 소리를 페이드/취소하고 투구음/콜을 우선한다. 입장 음악이 끝날 때까지 게임이나 버튼을 잠그지 않는다.
- **로딩과 실패:** 사용자의 선택 뒤 입장 샘플1개만 별도로 준비하는 작은 확장을 검토한다. 현재 `prepare()`는 기존12개 공통 음원 준비/정리를 담당하므로 입장 곡을 그 목록에 무조건 합쳐 첫 타격을 기다리게 하지 않는다. 입장 화면 준비 뒤 약300~500ms 이내의 작은 표시 기한을 첫 후보로 두고 늦으면 소비/생략한다. 뒤늦은 음악을 투구 중 재생하지 않고, 소리가 없어도 정상 입장한다. 기존 이미지 준비·타격 입력·DB 확정을 음원 준비에 종속시키지 않는다. 입장 소개는 무음에서도 이름·번호·팀 색상으로 이해할 수 있게 한다.
- **채널과 설정:** 첫 팡파르는 기존 효과음 채널과 전체25% 기본 음량을 따르고 설정에 ‘입장 효과음’ 선택을 추가하는 작은 안을 권한다. 콜/관중으로 분류하거나 상시 관중 루프를 기존 단일 관중 반응 소스에 끼워 넣지 않는다. 후속 앰비언스는 별도 채널·기본OFF를 검토한다. 심판/타격을 우선하고 음소거·메뉴·중단·앱 전환·언마운트는 준비 대기까지 정리한다. 음소거 중에도 입장 사건은 소비해 다시 켰다고 과거 음악이 울리지 않게 한다.
- **입장 사건 구현 기준:** 공/시도 사건과 별도로 새 훈련/타석을 시작한 명시적 사용자 의도와 성공한 현재 입장을 묶는 휘발성 표식을 구현했다. 가짜 투구/결과 사건으로 재사용하지 않으며 타석의 공 수가0이거나 육성 자식이 마운트됐다는 사실만으로 신규 입장으로 판단하지 않는다. 부모/자식 중 직접 타석 한 곳만 재생을 소유하고 복구/서버 채택·HMR에는 신규 입장 표식을 전달하지 않는 기준을 유지한다.
- **웹 근거:** 사용자 상호작용 없는 소리 재생은 브라우저 정책으로 제한될 수 있으므로 클릭/탭을 시작점으로 설계한다. 상호작용이 있어도 모든 브라우저의 재생 성공을 보장하지 않으므로 실패/무음 경로가 필요하다. [MDN 자동 재생 안내](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), [Chrome 자동 재생 정책](https://developer.chrome.com/blog/autoplay).

### 7. 수비 표시: 현재 데이터로 가능한 범위

| 기존 모델 자료 | 먼저 표시할 내용 | 데이터가 없는 표현 |
| --- | --- | --- |
| `fielders` 초기x/z·`fielderId`·`reachPoint` | 기본 포지션9점, 처리 지점, 확정 뒤 담당 강조 | 수비수의 시간순 실제 이동 경로·실사 포구 자세 |
| `path`·`decisionPoint`·`fieldingTimeMs` | 이미 지나간 타구와 실제 계산된 처리/포구 지점 | 처리 이후 날아가는 송구 공의 궤적·릴리스·받는 선수 |
| `defenseBaseTimesMs`·`runnerBaseTimesMs` | 확정 땅볼 아웃의1루 송구/주자 도달 비교와 설명용 점선 | 1→2→3루 연속 송구·중계 플레이. 배열은 같은 처리점에서 각 베이스로 직접 던지는 독립 비교값이다. |
| `wallContacts`·`landingPoint` | 시각이 있는 담장 접촉, 위치만 있는 착지 지점 | 모든 착지의 정확한 사건 시각. 담장 반사 후 원래 `landingTimeMs`를 실제 바운드 시각으로 쓸 수 없다. |
| 확정 `outcome`·`reasonKey`·`bases` | 뜬공 포구/1루 경합/인정 진루의 결과 안내 | 저장된 결과를 새 표시용 물리로 다시 판정하거나 새로운 보상을 적립하는 기능 |

현재 결과 화면의 기본 미니맵은9명 기본 위치·담당 강조·타구 경로/판정점·결과 이유를 이미 표시한다.7의 첫 수비 보완은 이를 재사용해 **처리 시점과1루 경합의 설명**을 더하는 단계다. 실제 장면의9명 전신 수비수·달리기/포구/송구 모션은 다음 비교다. 현재 표시 스냅샷에는 일부 수비 메타데이터가 없으므로 기존 결과의 검증된 필드를 표시 모듈로 넘기는 설계가 필요하지만, 엔진/저장 계약에 새 움직임을 끼워 넣지는 않는다.

진행 중에는 기본 위치와 이미 도달한 타구/처리의 중립 표식을 보여주고, 안타/아웃·담당 수비수/상세 설명은 기존 확정 기준을 따른다. 서버 확인이 늦어도 포구 장면을 처음부터 반복하지 않는다. 뜬공 아웃에 송구를 추가하거나 모든 안타에서 임의의 송구 목적지를 만들어서는 안 된다. 실제 투구·타격 중 상세 미니맵을 강제 확대하지 않고 결과에서 확대할 수 있게 검토한다.

### 8. 타자 세리머니

- **첫 대상은 확정 홈런:** 결과 영역의 작은 전신 컷에서 약0.8~1.2초, 타구 쪽을 바라보고 가볍게 주먹을 쥐거나 팀 표시를 짚는 절제된 동작을 권한다. 타구를 맞춘 순간에 홈런을 예측해서 축하하지 않는다. 인정2루타·강한 아웃을 홈런 컷으로 바꾸지 않는다.
- **위치 보존:** 현재 타자는 첫4m 이후 사라지므로 확정 때 홈플레이트에 되돌려 세리머니를 시키면 위치가 역행한다. 첫 버전은 별도 결과 컷으로 구분한다. 구장 안에서의 베이스 터치/홈 귀환 세리머니는 전체 주루 시점과 같이 설계한다.
- **이미지 제작:** 기존 실사풍 인물·카메라·광원·스폰서 없는10팀 의상을 기준으로 새 통짜 자세를 필요한2~3장부터 검토한다. 신체를 잘라 회전하거나 기존16자세·후속5자세를 덮어쓰지 않는다. 등번호 노출·긴 소매·손/발 접지·좌우 시작을 새로 검수하고 선택 팀의 필요한 컷만 준비한다.
- **확장 후보:** 안타의 작은 고개 끄덕임/장갑 정리, 삼진의 짧은 아쉬움, 시즌 첫 안타/첫 홈런 표시다. 기존 삼진은 중립 배트 내림까지만 구현돼 있으므로 고개 숙임이 이미 있다고 표현하지 않는다. 첫 홈런 안내도 기존 확정 성적을 읽는 표시이며 새 보상/업적 DB가 아니다.
- **입력과 수명:** 기존 다음 공/다음 타석 선택은 즉시 컷을 정리한다. Space는 야구의 기존 스윙 입력이므로 새 세리머니/건너뛰기에 중복 배정하지 않는다. 복구·중복 응답·자동 경기·언어/테마 변경에는 과거 세리머니를 재생하지 않는다. 끄기/모션 축소·이미지 실패에는 정적인 기존 결과를 제공한다.

### 9. 구장 배경 생동감

1. **전광판/입장 소개:** 기존 안전한 외야 영역을 검토해 선수 이름·등번호·팀 색상의 짧은 소개, 카운트/확정 결과를 표시한다. 새 패널이 공/존/수비 표식을 가리지 않도록 PC·작은 세로/가로를 비교한다. 화면에 보이는 이름은 현재 브라우저의 기존 선택값이며 외부 방송/TTS에 전송하지 않는다.
2. **깃발:** 별도 작은 투명 레이어의 느린 흔들림을 먼저 검토한다. 현재 배경은 정지 래스터이므로 사진 전체를 흔들어 나무/구장/트랙이 같이 휘게 만들지 않는다. 기존 구조에 맞는 분리 자산이 필요하고 제작 전 원본 배경과 접합을 비교한다.
3. **관중 일부:** 전체 관중을 매 프레임 움직이는 대신 몇 구역만 낮은 빈도로 반응시키고, 큰 반응은 확정 홈런/안타에 연결한다. 흰 섬광·화면 흔들기·수많은 파티클을 첫 선택으로 넣지 않는다.
4. **낮은 배경음:** 조용한 관중 웅성거림을 구장 소리 선택 항목으로 검토한다. 콜/배트/팡파르보다 낮추고 진입만으로 재생하지 않는다. 반복 경계·앱 전환/백그라운드 정지·복귀 후 사용자 입력 재개를 실제 휴대폰에서 듣는다. 준비 실패는 무음이며 상시 BGM·팀 응원가10개를 먼저 받지 않는다.

정적 배경과 작은 변경 부분을 나눠 그리고, 반복 무늬/팀 합성은 기존 선택 자산 관리와 재사용 원칙을 따른다. 현재 Canvas 루프에 무거운 처리나 새 전역 애니메이션 루프를 여러 개 추가하는 것을 기본안으로 삼지 않는다. 표시 시계는 `requestAnimationFrame`에 맞추되 배경 장식 갱신 빈도와 실제 공/입력 시계를 분리한다. 정적/동적 레이어·사전 렌더·프레임 갱신의 기술 참고는 [MDN Canvas 최적화 안내](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)다. 이 권고만으로 실제 모바일 성능이 개선됐다고 주장하지 않는다.
