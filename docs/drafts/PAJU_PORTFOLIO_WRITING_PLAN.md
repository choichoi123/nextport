**편집자용 로컬 참고 경로:** `Paju_voucher/...`는 nextport와 같은 상위 폴더의 별도 저장소 기준 경로입니다. 이 저장소에 포함되지 않는 문서·이미지는 활성 링크 대신 경로로 표기합니다.

| `Description` | **교통약자 이동지원 이용자의 가입·주소 선택·이동 접수·이용내역 확인과 관리자 회원 업무를 연결한 WebView 서비스입니다. 제가 이용자·관리자 프론트엔드 전체와 백엔드 API 연동을 담당했습니다.** |
| `Tags` | React, JavaScript, Redux Toolkit, React Router, Axios, Kakao Maps |

현재 카드는 Description에서 **‘제가 … 담당했습니다’처럼 본인 역할이 명시된 문장**을 읽습니다. 위 문구를 사용하면 역할을 별도 하드코딩하지 않고 Notion 원문으로 표시할 수 있습니다. ‘핵심 기여’는 현재 공통 상세 확인 문구이므로, 이번 Description 보강만으로 사례 요약이 그 칸에 자동 표시되지는 않습니다.

### 월 단위 기간과 현재 화면의 제약

기존 `WorkPeriod`는 날짜형 속성입니다. HANDOFF의 `2026-02 ~ 2026-05`는 월 단위 제안이므로 날짜 필드에 그대로 저장할 수 있다고 가정하지 않습니다. **일자 확인 없이 2월 1일·5월 31일을 만들거나 진행 중으로 저장하지 않습니다.**

우선 상세 본문에 확정된 월 단위 기간을 적고 날짜 속성 입력은 보류하는 안입니다. 이 경우 현재 카드에는 ‘기간 미정’이 표시되고 최근 시작 월 정렬에서는 뒤로 갑니다. 월 단위 기간을 카드에도 정확히 표시하려면 기존 속성 계약과 표시 방식을 함께 보완하는 별도 변경이 필요하며, 이 계획 작성 중 스키마나 코드를 바꾸지 않습니다.

### 대표 사례 A — 주소 검색과 지도 위치 선택을 연결한 입력 흐름

서비스 이용자가 주소 후보를 찾고 지도에서 위치를 확인하는 과정을 보여줍니다. **자주가는곳 등록의 검색 결과 → 지도 위치 선택**은 3월 실제 화면 두 장으로 연결해서 설명할 수 있습니다. 접수의 경로 미리보기는 별도 기능으로 구분합니다.

기술적으로는 **서버 정수 좌표의 표시 스케일 변환, 지도 중심의 역지오코딩, 경로 데이터 유무에 따른 표시 분기, 화면 크기·회전 변화에 따른 지도 재배치**를 초기 구현의 근거 있는 내용으로 사용합니다. 아래 Git 비교에서 해당 처리가 초기 기간에 존재함을 확인했습니다. 정수 좌표의 스케일을 지도 위·경도에 맞춘 처리를 ‘좌표 오류 자동 보정’으로 표현하지 않습니다. 9월 `isOrigin` 정책은 이 사례에 넣지 않습니다.

### 대표 사례 B — 로그인과 센터 이용 승인을 구분한 화면 흐름

웹 계정 로그인과 센터 회원 연동·승인을 구분하는 업무 구조를 설명합니다. 이용자 화면의 상태 안내와 관리자 회원 업무를 연결한 프론트엔드 역할에 집중합니다. 서버가 최종 인증·인가와 회원 상태를 판단하고, 화면은 그 응답에 따라 진입·표시를 제어하는 경계를 적습니다.

초기 Git에서 로그인·센터 연동 여부를 별도 Guard로 확인하고 실제 접수·내역·즐겨찾기 라우트에 연결한 구조를 확인했습니다. 이 구분을 대표 사례로 사용하고 관리자 회원 연동 화면의 세부 업무는 당시 근거가 확인된 범위로 한정합니다. 전달된 가입 05·06 화면은 입력 전 폼이므로 승인 처리나 가입 완료를 입증하는 자료로 사용하지 않습니다. 초기 관리자 화면 자료가 없다는 이유로 9월 승인 명단을 대신 넣지 않습니다.

### 결과 문단의 방향

> 백엔드 개발자 1명과 협업하며 모바일 WebView 이용자 화면과 관리자 웹의 프론트엔드 전체를 담당했습니다. 가입·주소 선택·이동 접수·이용내역과 관리자 회원 업무를 기존 API에 연결했습니다. 제공된 2026년 3월 개발·테스트 화면으로 초기 입력·조회 UI를 확인할 수 있습니다.

여기에 초기 기간에 해당하는 검증 근거가 확보되면 확인한 환경·조건을 덧붙입니다. 최신 인증 테스트 수나 개발 화면만으로 운영 배포·실제 문자 인증·실제 배차 성공을 결과에 적지 않습니다.

## 4. 이미지 배치 계획

최종 표지는 **실제 화면 기반 편집본**으로 사용합니다. 다른 프로젝트의 구성 일러스트와 자료 성격이 다르므로 ‘실제 화면 아님’ 표시를 복사하지 않고, ‘초기 개발·테스트 화면’이라는 캡션을 붙입니다. 화면은 전체 비율을 유지하고 읽을 수 있는 크기로 배치합니다.

본문은 **01·03·04·07의 4장**을 우선 사용하고, 탑승 조건 설명이 필요하면 02를 추가합니다. 05·06은 가입 단계의 화면 예시가 필요한 경우에만 사용합니다. 확보한 7장을 모두 넣는 것을 목표로 삼지 않습니다.

## 6. 더 받아야 할 근거와 반영 순서

기간·팀·전체 프론트엔드 담당·이미지 사용 조건은 이미 확인됐으므로 다시 묻지 않습니다. 파주 담당 AI의 추가 보완이 필요하다면 아래처럼 **초기 개발에 한정한 질문**으로 좁힙니다.

1. 지도·Guard의 초기 소스 존재는 확인했습니다. 관리자 회원 연동·승인의 세부 업무를 보강할 때는 초기 기간의 근거를 연결하고 이후 바뀐 동작은 분리해 주세요.
2. 당시 실제 검토한 대안과 채택 이유가 남아 있으면 제공해 주세요. 기록이 없으면 현재 구현 설명까지만 사용하겠습니다.
3. 초기 관리자 회원 연동·승인 화면의 공개 가능한 기존 자료나 검증 기록이 있으면 제공해 주세요. 새 업무 요청·실제 문자·접수 실행은 자료 준비의 조건이 아닙니다.

후속 작성 순서는 다음과 같습니다.

1. 이 계획에 따라 **기존 초안의 후속 보완본**을 작성하고, 공개 본문과 편집자 근거를 분리합니다. 초기 Git 근거가 부족한 세부 동작은 제거하거나 확인 필요로 둡니다.
2. 본문·카드 문구·이미지 순서와 월 단위 기간 표시 방법을 검토할 수 있게 제시합니다.
3. DB 반영 단계에서 개인 복제본의 최신 목록을 읽어 파주 항목 중복 여부와 속성 종류를 확인합니다. 마지막 확인 상태는 6개 항목·파주 없음이며, 이번에는 DB를 새로 조회하지 않았습니다.
4. 반영할 범위가 정해지면 개인 DB에 새 항목을 작성하고 본문·표지·캡션·속성을 전달 자료와 읽기 대조합니다. 읽기 전용 API 연결의 권한을 확대하는 방식으로 처리하지 않습니다.
5. 로컬 전체 프로젝트 화면에서 제목·역할·기간·태그·표지·상세 링크를 확인합니다. 홈 대표작은 현재 WISEOP·이케이시스·SaaS 우선순위이므로 **파주 추가만으로 대표작에 자동 편입되지 않습니다.** 대표작 교체가 필요하면 별도로 순서를 정합니다.

완료 기준은 **기간과 개인 역할의 일치, 유지보수 혼입 없음, 화면 의미에 맞는 캡션, 주장별 초기 근거, DB 원문과 로컬 표시의 일치**입니다. 기존 WISEOP가 운영자의 관제 흐름과 전체 시스템 연동을 보여준다면, 파주는 이용자의 모바일 입력·위치 선택과 관리자 업무를 함께 구현한 프론트엔드 경험을 중심으로 구분합니다.
