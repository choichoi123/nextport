## 3. 공개 본문 초안

아래는 **2026년 2월~5월 참여 기간**의 공개용 후보 본문입니다. 현재 소스에서 확인한 세부 동작이 이 기간에 구현됐는지는 원 프로젝트 담당 AI 자료와 추가 대조합니다. 확인된 9월·11월 후속 사례는 뒤 절로 분리했습니다. 내부 참고용 경로·Git 기록은 공개 본문에 넣지 않습니다.

### 01. 프로젝트 개요

**참여 기간: 2026.02~2026.05 / 개발 인원: 백엔드 1명·프론트엔드 본인 1명**

파주 교통약자 이동지원 이용자가 휴대폰에서 회원가입과 센터 승인 절차를 거쳐 출발지·목적지를 선택하고, 차량을 접수한 뒤 진행 상태와 이용내역을 확인할 수 있는 WebView 기반 서비스입니다.

백엔드 개발자 1명과 협업하며 이용자 모바일 화면과 관리자 웹의 프론트엔드를 담당했습니다. React 화면 구현부터 라우팅·회원 상태 관리, 지도와 위치 선택, 백엔드 API 연동까지 하나의 이용 흐름으로 구성했습니다.

### 02. 해결할 문제

이용자는 작은 화면에서 주소를 찾고 실제 탑승 위치를 정한 뒤 이동 목적·동승 정보 등을 입력해야 합니다. 주소 검색 결과, 지도상의 위치, 서버가 받는 좌표가 서로 어긋나지 않아야 하며, 접수 전 경로 확인과 접수 후 차량 확인도 구분해 제공해야 했습니다.

또한 웹 회원가입과 센터 회원 승인·연동은 별도 단계입니다. 이용자에게 현재 이용 가능한 기능을 안내하는 화면과, 관리자가 회원을 찾아 관제 회원에 연결하고 승인 상태를 관리하는 화면이 함께 필요했습니다.

### 03. 내 역할과 시스템 구성

| 구분 | 담당 범위 |
| --- | --- |
| 이용자 프론트엔드 | 가입·로그인·계정 찾기, 회원정보, 즉시콜 접수, 이용내역, 자주 가는 곳 |
| 지도·위치 UI | 주소 검색·현재 위치·지도 미세 선택, 예상 경로·거리·시간, 접수 경로와 차량 위치 |
| 관리자 프론트엔드 | 로그인, 웹 회원 검색·관제 회원 연동·승인 상태 관리 |
| 상태·연동 | React Router의 화면 흐름, Redux Toolkit의 사용자·관리자 표시 상태, Axios를 통한 기존 업무 API 연동 |

이용자 WebView와 관리자 브라우저의 화면이 기존 백엔드의 회원·접수·관제 API에 연결되는 구조입니다. 제 담당은 웹 프론트엔드이며, 서버·DB와 Android/iOS 네이티브 앱 자체 개발은 이 소개의 기여 범위에 포함하지 않습니다.

### 04. 주요 구현과 기술 사례

**주소 검색에서 탑승 위치 확정까지 연결한 지도 UI**

주소 검색, 자주 가는 곳, 최근 이용 경로와 출발지 현재 위치를 위치 선택의 진입점으로 제공했습니다. 검색한 주소를 지도에서 확인하고 중심 위치를 옮겨 상세 위치를 선택할 수 있도록 구성했습니다.

- **제약:** 서버 좌표와 지도 좌표의 표현이 달라 주소와 지도상의 선택 위치를 일관되게 연결해야 했습니다.
- **구현:** 서버의 정수 좌표와 지도 위·경도 사이에 변환을 적용했습니다. 지도 중심 좌표는 역지오코딩해 주소와 함께 선택값으로 반영했습니다.
- **표시:** 선택한 위치의 예상 경로·거리·시간을 접수 전에 확인하도록 했습니다. 실제 경로 데이터가 없을 때는 임의의 선을 경로처럼 그리지 않고 출발·도착 위치를 표시하는 분기를 두었습니다. 화면 크기·회전 변화에 따른 지도 크기 보정도 구현했습니다.

**로그인과 센터 승인 상태를 구분한 이용 흐름**

가입·로그인 완료와 접수 서비스 이용 가능 여부를 같은 상태로 취급하지 않았습니다.

- **제약:** 로그인한 웹 회원도 센터 회원과 연결되기 전에는 접수 기능을 사용할 수 없는 업무 구조였습니다.
- **구현:** 보호 화면 진입 때 서버 세션을 확인하고, 접수·이용내역·즐겨찾기에는 별도의 센터 회원 연동 확인 단계를 적용했습니다. 이용자와 관리자의 화면·세션 확인 흐름도 구분했습니다.
- **화면 결과:** 승인·연동 전 이용자에게 상태를 안내하고 홈으로 이동시키며, 관리자는 회원 검색·관제 회원 연결·승인 상태 변경 화면으로 처리할 수 있게 구성했습니다. 프론트엔드의 화면 접근 제어와 서버의 최종 인증·인가 책임은 구분했습니다.

### 05. 결과와 검증

이용자의 가입·승인 확인부터 주소 선택·즉시콜 접수·이용내역 조회까지 이어지는 모바일 웹 화면과 관리자 회원 업무 화면을 구축했습니다. 접수 상태에 따른 차량 보기·취소 버튼과, 지도 표시 중 차량 위치를 주기적으로 조회하는 흐름도 구현했습니다.

2. **별도 보관된 지도 개선 UI:** `docs/UI_SNAPSHOTS.md:17`과 `docs/MOBILE_RECEIVE_UX.md:3`은 주소 아래 경로 펼침·접기, 입력 위치 유지, 지연 생성·캐시·재시도의 개선안을 기록합니다. 개선 태그는 보존돼 있지만 현재 선택은 기본 UI입니다. 개선안의 테스트·화면 수치를 현재 적용된 UI의 성과로 옮기지 않았습니다.

4. **검증 범위:** 최신 OTP 문서에는 인증 60개·미리보기 30개 모의 테스트와 별도 경로 빌드 통과가 기록돼 있습니다. 실제 문자 인증·실기기·운영 배포 검증을 의미하지 않습니다. 기존 아키텍처 문서의 전체 Jest 수집 실패 기록과 특정 기능의 후속 모의 검사 성공 기록도 구분합니다.
5. **성과·기술 선택:** 업무 시간 단축·접수 성공률·성능 개선 비율·실서비스 이용 규모는 미확인입니다. 현재 구현의 역할은 확인했지만 React·Redux·지도 구조를 택할 당시의 대안 검토 기록은 추가 확인이 필요합니다.

## 6. 원 프로젝트 담당 AI에게 받을 보완

- 사용자 확인 기간 **2026.02~2026.05**를 적용하고 해당 기간의 구현을 이번 초안의 기능과 대조합니다. 필요한 경우 정확한 시작·종료 일자와 최초 개발·납품·후속 작업의 구분을 보완합니다. 월 단위 기간을 다시 승인받지는 않습니다.
- 본인이 가장 깊게 해결한 기술 문제 2~3개를 골라 당시 문제·실제 검토 대안·채택 이유·구현·검증 근거를 보완합니다. 현재 후보를 더 강한 사례로 교체해도 됩니다.
- 사용자·관리자 프론트엔드 범위와 외부 서버·네이티브 담당 경계를 재확인합니다. 설계·디자인·앱 배포까지 본인 담당이었다고 추정하지 않습니다.
- 어떤 커밋·빌드가 운영 반영됐는지, Android/iOS 실제 기기의 확인 범위, 남은 오류와 기술 부채를 구분해 전달합니다.
- 9월 관리자 기능·별도 지도 개선안·11월 OTP 추가 개선의 포트폴리오 포함 범위를 정리합니다.
- 공개 가능한 화면·시연·서비스 주소를 [전달 가이드](../PORTFOLIO_HANDOFF_GUIDE.md) 형식으로 준비하고, 기존 구현과 다른 제안 화면은 구분합니다.
