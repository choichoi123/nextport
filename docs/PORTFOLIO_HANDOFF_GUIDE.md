# 프로젝트 담당 AI를 위한 포트폴리오 자료 전달 가이드

작성 기준: **2026-11-11**. nextport의 기존 Notion 양식에 맞춰, 프로젝트를 가장 잘 아는 담당 AI가 구현의 깊이와 근거를 전달하기 위한 기준입니다. DB 계약과 편집 절차는 [Notion·콘텐츠 기준](NOTION.md), 작업 권한은 [AGENTS](../AGENTS.md)를 따릅니다.

## 1. 사용 방법과 역할

사용자가 아래 요청문을 프로젝트 담당 AI에게 전달합니다. 담당 AI는 자신의 프로젝트에서 자료 묶음을 만들고, 사용자는 그 경로를 포트폴리오 담당 AI에게 알려줍니다. 두 AI가 서로의 대화 기록을 알고 있거나 다른 저장소의 규칙을 자동으로 상속한다고 가정하지 않습니다.

| 담당 | 책임 |
| --- | --- |
| 원 프로젝트 담당 AI | 업무 맥락, 본인 담당 범위, 실제 구현·판단, 기술 사례, 근거와 공개용 자료를 준비합니다. 구현 의도가 기록에 없으면 추정하지 않습니다. |
| 포트폴리오 담당 AI | 전달 자료와 기존 항목을 대조하고, 핵심 사례를 선별해 제목·카드·상세 본문·이미지를 편집합니다. 승인된 대상에 반영하고 저장 결과를 다시 확인합니다. |
| 사용자 | 참여 기간·개인 기여·공개 허용 등 문서만으로 확정할 수 없는 사실을 확인하고 반영 범위를 결정합니다. 기존 확인과 승인은 다시 묻지 않습니다. |

자료 요청은 원 프로젝트의 기능 수정, 운영 명령, 새 테스트·서버 실행, Notion 업로드·공유·배포 권한까지 포함하지 않습니다. 우선 기존 코드·문서·검증 기록·허용된 캡처로 작성합니다. 추가 실행이 필요하면 그 프로젝트의 현재 승인 범위와 규칙을 확인합니다.

### 다른 프로젝트 AI에게 전달할 요청문

아래를 복사하고 프로젝트명과 알고 있는 사실만 채웁니다. 가이드 경로에 접근할 수 없는 환경이라면 이 문서의 내용을 함께 전달합니다.

```text
[프로젝트명]을 내 nextport 포트폴리오에 소개하기 위한 자료를 준비해줘.

먼저 다음 가이드를 읽어줘.
C:\Users\테스트\Documents\GitHub\nextport\docs\PORTFOLIO_HANDOFF_GUIDE.md

너는 이 프로젝트의 구현 맥락을 가장 잘 아는 담당 AI다. 기능 목록 요약에 그치지 말고,
실제 해결한 문제·제약·선택 이유·구현 방식·검증 결과를 근거와 함께 정리해줘.
이 프로젝트의 규칙과 기존 코드·문서·검증 기록을 읽고, 아래 세 부분을 구분해줘.
1) Notion 속성 및 공개 본문 초안
2) 편집자만 볼 주장별 근거·확인 필요 사항·기존 내용 수정 제안
3) 공개용 이미지·영상과 정확한 캡션·사용 한계

가이드 7절 템플릿을 사용해 HANDOFF.md와 필요한 images/를 만들어줘.
저장 위치는 이 프로젝트가 허용하는 로컬 자료 경로의 portfolio-YYYYMMDD 폴더로 해줘.
원본 업무 자료를 그대로 복사하거나 전체 소스·로그·비밀값을 묶지 말아줘.
자료 작성 외의 제품 코드 수정·운영 조작·Notion 편집·공유·배포는 진행하지 말아줘.
기존 기록만으로 부족한 것은 확인 필요로 남기고, 새 검증을 수행한 것처럼 쓰지 말아줘.

내가 이미 확인한 사실 또는 공개 허용 범위: [있으면 기입, 없으면 확인 필요]
기존 포트폴리오 항목/초안: [있으면 주소 또는 파일 경로, 없으면 신규]
마지막에는 만든 폴더 경로, 가장 강한 기술 사례, 남은 확인 사항을 알려줘.
```

## 2. 먼저 확정할 프로젝트 사실

공개 초안과 별도로 각 사실의 근거를 적습니다. 사용자 확인, 문서·코드 근거, 확인 필요를 구분합니다. 전달 문서 안의 제안과 사용자 확정값이 다르면 충돌을 표시하고, 편집자가 임의로 덮어쓰지 않도록 합니다.

| 항목 | 필요한 내용 |
| --- | --- |
| 정체성 | 무엇을 위한 어떤 결과물인지, 사용자와 해결할 업무 문제, 신규 개발·리뉴얼·고도화 중 실제 범위 |
| 기간 | 본인의 참여 시작·종료일과 근거. 작성일·최근 commit·캡처일을 종료일로 바꾸지 않습니다. 기반 제품의 최초 개발과 이번 참여를 구분합니다. |
| 팀과 기여 | 팀 인원과 본인이 맡은 화면·API·데이터·연동·검증·배포 범위. 다른 사람·외부 서비스·기존 자산의 범위도 구분합니다. |
| 현재 수준 | 구현, 검증, 운영 배포를 각각 어느 시점·버전까지 확인했는지 |
| 공개 범위 | 프로젝트·회사·고객 명칭, 화면·코드·링크 중 공개 가능한 범위와 확인 출처 |
| 차별점 | 다른 프로젝트와 구분되는 업무 제약·기술 판단·해결 사례와 이를 뒷받침하는 근거 |

‘전체 개발’이라는 확인이 있어도 외부 엔진·협력 서버까지 자체 개발했다고 확대하지 않습니다. 인원수만으로 기여율을 계산하거나 저장소 작성자를 개인 기여의 유일한 근거로 삼지 않습니다. 날짜가 월 단위로만 확인되면 임의의 일자를 만들지 말고 정확도를 적습니다.

### Notion 속성 초안

다음 값은 제안으로 전달하고 DB 속성을 직접 만들거나 이름을 바꾸지 않습니다. 정확한 종류·사이트 표시 동작은 [속성 계약](NOTION.md#프로젝트-속성-계약)을 따릅니다.

| 항목 | 작성 기준 |
| --- | --- |
| `Name` | 서비스·대상·개발 범위를 알 수 있는 제목. 기존 프로젝트 제목을 복사한 뒤 일부만 바꾸지 않습니다. |
| `Description` | 누구의 어떤 문제를 해결한 결과물인지와 핵심 담당 범위를 1~2문장으로 설명합니다. 기술 이름을 나열하는 소개는 피합니다. |
| `Tags` | 직접 사용한 핵심 기술을 선별하고 각 기술의 역할·근거를 내부 표에 적습니다. 의존성 목록 전체를 태그로 옮기지 않습니다. |
| `WorkPeriod` | 시작일·종료일 또는 확인 필요. 실제 진행 중인 경우에만 종료일 없음으로 제안합니다. 사용자 확정 기간을 존중합니다. |
| `GitHub`, `Youtube` | 공개 가능한 실제 주소만 제안합니다. 비공개 저장소나 없는 시연을 공개 자료처럼 표시하지 않습니다. |
| 운영·서비스 링크 | 주소와 공개 접근/로그인 필요/내부 전용을 구분합니다. `URL` 등 기존 속성과 본문 중 적합한 위치는 편집자가 정합니다. |
| 표지 | 대표 이미지 파일과 추천 이유. 페이지 커버이며 새 DB 열이 아닙니다. 없으면 미제공으로 남깁니다. |

## 3. 읽기 쉬운 공개 본문, 깊이 있는 기술 사례

본문은 **개요 → 문제 → 내 역할·시스템 구성 → 주요 구현과 기술 선택 → 결과·검증 → 관련 자료**로 작성합니다. 방문자가 처음 읽을 때 목적과 기여를 이해할 수 있도록 개요와 대표 화면을 앞에 둡니다. 내부 근거·편집 지시·로컬 경로는 공개 본문에 넣지 않습니다.

- **개요:** 결과물·대상 사용자·핵심 가치와 담당 범위를 짧게 설명합니다.
- **문제:** 실제 업무 흐름과 기존의 불편·제약을 설명합니다. 실제 발생한 문제와 예방하려는 위험을 구분합니다.
- **역할·구성:** 본인이 구현한 경계와 외부 의존성을 설명합니다. 필요하면 브라우저→API→데이터·외부 시스템의 간단한 구성도를 제공합니다. 개념도를 실제 배포 구성도처럼 제시하지 않습니다.
- **구현·선택:** 주요 기능은 묶어 요약하고, 판단이 드러나는 대표 사례 2~3개를 우선 제안합니다. 증거가 충분한 사례가 적으면 억지로 늘리지 않습니다.
- **결과·검증:** 실제로 확인한 동작·완료 범위와 남은 한계를 적습니다. 측정 수치가 없어도 검증한 결과와 의미를 구체적으로 설명합니다.
- **자료:** 공개 저장소·영상·문서를 연결하고 운영 링크는 접근 조건을 표시합니다.

### 대표 사례마다 답해야 할 질문

| 순서 | 필요한 깊이 |
| --- | --- |
| 상황·문제 | 어떤 사용자 조작·입력·데이터·실패 조건에서 어떤 문제가 있었는가? 기존 동작은 무엇이었는가? |
| 제약 | 시간·기존 구조·외부 API·업무 규칙·데이터·장치 등 실제 제약은 무엇인가? |
| 선택·이유 | 실제 검토한 선택지와 채택 이유·대가는 무엇인가? 당시 기록이 없으면 선택 의도를 추정하지 않고 현재 구현과 확인 가능한 효과만 설명한다. |
| 구현 | 어느 계층의 어떤 상태·계약·알고리즘·흐름을 어떻게 바꿨는가? 본인이 한 부분은 어디인가? |
| 결과·근거 | 어떤 조건을 무엇으로 확인했는가? 재현 가능한 기록·테스트·화면은 무엇이며 아직 증명하지 못한 것은 무엇인가? |

예를 들어 ‘비동기 처리 안정화’보다 ‘필터를 바꾼 뒤 늦게 온 이전 응답이 최신 화면을 덮는 조건을 구분하고, 현재 요청에 해당하는 응답만 적용하도록 처리했다’가 판단을 전달합니다. 단, 이 예시를 다른 프로젝트의 실제 실적으로 복사하지 않습니다. UI 중심 프로젝트라면 탐색·입력·반응형·접근성·복잡한 상호작용의 구체적인 판단도 좋은 사례가 됩니다.

‘구현했다’와 ‘왜 그 방식을 택했는지’를 구분합니다. 기술별 사용 목적만으로 선택 이유를 대신하지 않습니다. ‘최적화·확장성·안정성 향상’ 같은 표현은 바뀐 동작과 근거를 함께 제시합니다.

## 4. 편집자용 근거와 검증 수준

핵심 주장마다 아래 근거 표를 제공합니다. 모든 문장에 줄 번호를 붙일 필요는 없지만 개인 기여·기간·핵심 구현·정량 결과·운영 여부에는 확인 출처가 있어야 합니다. 긴 원문·전체 로그 대신 필요한 위치와 요약을 전달합니다.

| 주장 | 근거 위치 | 확인 수준·시점·환경 | 공개 사용 조건/한계 |
| --- | --- | --- | --- |
| [본문 또는 속성의 주장] | [저장소 기준 경로:줄, commit, 문서 절/날짜, 테스트명 또는 사용자 확인] | [아래 구분과 실제 확인 범위] | [공개 가능/편집자 참고/확인 필요] |

- **구현 확인:** 코드·설정에 해당 처리가 있습니다. 실행 성공을 뜻하지 않습니다.
- **기록된 검증:** 기존 테스트·빌드·회귀 기록의 날짜·대상·결과입니다. 자료 작성 중 다시 실행했다는 뜻이 아닙니다.
- **직접 동작 확인:** 어떤 환경·버전에서 어떤 입력과 결과를 실제 확인했는지 적습니다.
- **운영 배포 확인:** 배포된 버전·시점과 확인 근거가 있을 때만 사용합니다. 개발 화면이나 로컬 성공으로 대체하지 않습니다.
- **사용자 확인/미확인:** 구두 확인한 사실과 아직 확인할 수 없는 사실을 구분합니다.

코드의 현재 상태와 과거 검증 버전이 다르면 차이를 적습니다. 작성 시점의 commit 또는 작업 트리 변경 여부를 기록해 나중에 근거가 이동했을 때 찾을 수 있게 합니다. 비공개 원격 주소·인증정보를 포함한 명령 결과를 그대로 붙이지 않습니다.

성과 수치는 비교 기준·기간·표본·환경·측정 방법·본인 기여 범위가 있을 때만 제시합니다. 코드 줄 수·파일 수·테스트 수는 개발 규모나 검증 범위의 보조 근거이며 업무 효율·품질 향상 비율을 의미하지 않습니다. 외부 모델을 연동했다는 사실을 모델 자체 개발이나 정확도 개선 성과로 바꾸지 않습니다.

## 5. 이미지·영상 준비 기준

화면 수보다 설명하는 내용의 차이를 우선합니다. 대표 화면과 기술 사례를 설명하는 자료를 선별하고, 같은 화면의 작은 차이를 반복해서 넣지 않습니다. 전체 화면은 맥락을, 필요한 확대 화면은 조작·상태 차이를 읽을 수 있게 제공합니다. 고정 장수나 해상도를 맞추기 위한 불필요한 캡처는 요구하지 않습니다.

이미지를 제작하기 전에 최신 Notion 본문·승인 자료와, 필요한 경우 허용된 원 프로젝트 문서를 읽습니다. 핵심 사용자 흐름·개인 담당과 초기 개발·후속 유지보수의 범위를 구분해 요청된 소개 범위를 프롬프트에 담습니다. 기존 표지와 어울리는 색·선·여백·비율을 사용하면서 프로젝트별 기능이 구별되도록 시각 요소를 선택하고, 자료로 확인되지 않은 기능·성과·ID·개인정보를 새로 넣지 않습니다.

| 파일/자료 | 추천 위치·목적 | 공개 캡션 | 촬영 환경·증명 범위 | 공개 검수·미확보 |
| --- | --- | --- | --- | --- |
| `images/01-overview.png` | [대표 화면/개요] | [방문자가 볼 설명] | [실제 데이터/모의/시안, 개발/운영, 버전·촬영일, 확인되는 단계] | [가림 적용 범위·사용자 허용 또는 미확보] |

- **실제 파일과 제안 슬롯을 구분:** 파일명만 적은 미확보 이미지는 업로드 가능 자료로 표시하지 않습니다. manifest가 이미 있으면 위 표 대신 활용할 수 있습니다.
- **캡션의 정확성:** 선택 화면은 실행 전 선택, 후보 0건은 결과 없음으로 설명합니다. 응답 접수·업무 완료, 직선 안내·실제 경로, 시안·운영 화면을 구분합니다.
- **자료 유형:** 구성 일러스트는 실제 UI 캡처와 구분하고 이미지 안에 ‘구성 일러스트 · 실제 화면 아님’을 표시합니다. 실제 캡처는 해당 시점·환경과 확인되는 범위를 캡션으로 설명합니다.
- **시각 검수:** 완성 파일을 직접 열어 기능 표현·한글·가독성을 확인하고, 적용 화면에서 카드 축소·커버 크롭 후에도 핵심 요소와 구분 문구가 남는지 라이트·다크 상태로 확인합니다.
- **제작 기록과 원본:** 파일·프롬프트·참고 출처와 대상 프로젝트를 기존 제작 기록에 남깁니다. 실제 표지는 Notion 커버를 원본으로 읽으며, 표지 교체를 위해 프로젝트 ID별로 로컬 이미지를 하드코딩하는 방식은 피합니다.
- **동작 증거:** 정지 화면으로 보여주기 어려운 상호작용은 기존 공개 가능 영상이나 재현 순서를 제안합니다. 영상이 없으면 없다고 적습니다.
- **공개용 자료:** 계정·비밀값·개인정보·허용되지 않은 업무 정보를 제거한 파일을 제공합니다. 원본 코드·운영 로그·원본 문서를 자동 첨부하지 않습니다. 내부 경로·호스트가 보이면 공개 허용 여부를 확인합니다.
- **사용자별 예외:** 이미 명시적으로 허용된 명칭·ID·자료 범위를 내부 전달란에 기록하고 중복 확인하지 않습니다. WISEOP에서 허용된 ID 등 특정 프로젝트의 예외를 다른 프로젝트에 일반화하지 않습니다.
- **검수 한계:** 공개 허용 여부가 불명확한 파일은 편집자 참고 또는 사용 보류로 표시합니다. 자동으로 웹에 공개하거나 공개 URL을 만들지 않습니다.

## 6. 전달 폴더와 완료 기준

최소 구성은 문서 하나와 필요한 이미지입니다. 프로젝트의 기존 문서·로컬 자료 규칙을 따르고, 자료 폴더 생성이 commit·push 승인은 아닙니다.

```text
portfolio-YYYYMMDD/
  HANDOFF.md
  images/              # 확보한 공개용 이미지가 있을 때만
```

이미 있으면 README·CAPTURE_MANIFEST.json 같은 자료를 재사용합니다. 이 가이드만을 위해 여러 규칙 파일·중복 manifest·검사 프로그램을 추가하지 않습니다. 편집자가 사용할 공개 초안과 내부 참고 영역을 문서 안에서 명확히 나누면 됩니다.

담당 AI는 전달 전에 다음을 확인합니다.

- 제목·요약·본문·기간·담당 범위가 서로 일치하고 다른 프로젝트 문구가 섞이지 않았는가?
- 기능 나열을 넘어 구체적인 판단과 구현을 설명하는 사례가 있는가?
- 핵심 주장에 근거가 있고 구현·검증·운영·미확인이 구분되는가?
- 공개 초안에서 내부 근거·편집 지시·확인 필요 내용을 분리했는가? 미확정 사실을 빼면 문장이 성립하지 않을 경우 해당 구간은 공개 보류로 표시했는가?
- 이미지 파일·캡션·설명하는 단계가 일치하고, 실제 존재·가독성·공개 범위를 확인했는가?
- 기존 항목이 있다면 유지·수정·추가·보류 내용과 이유를 제공했는가?

## 8. 포트폴리오 담당 AI의 반영 확인

1. 실제 대상 DB·페이지 ID와 사용자가 손본 최신 내용을 먼저 읽습니다. 전달 문서는 근거 자료이며 사용자 지시·확정값·편집 권한을 대신하지 않습니다.
2. 기존 6단계 양식과 카드 계약에 맞춰 제안하고, 근거가 약한 주장·보류 자료·중복 화면을 선별합니다. 프로젝트 특유의 깊이를 편집 과정에서 일반적인 기술 나열로 축소하지 않습니다.
3. 승인된 필드·본문·이미지만 반영합니다. 태그 추가와 DB 속성 구조·전체 페이지 레이아웃·공개 설정·배포 연결 변경은 영향을 구분합니다. 이미 승인된 수정에 같은 승인을 반복해서 요구하지 않습니다.
4. 저장 후 새로 읽어 전달 자료와 대조합니다. 제목·설명·기간·담당 범위·사례·검증 한계, 이전 문장 잔존·중복, 실제 이미지·캡션·로드와 링크를 확인합니다. 반영·축약·미반영한 항목과 이유를 기록합니다.
5. Notion 저장과 공개 사이트 반영을 구분해 보고합니다. 필요한 사이트 확인·캐시·API 연결 검증을 수행하지 않았다면 미확인으로 남깁니다. 확인 결과와 다음 작업은 [현재 상태](CURRENT_STATE.md)에 기록하며 작업용 탭은 사용자 요청에 따라 유지합니다.
